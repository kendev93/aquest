# 免费 A 股日线数据源调研（2026-09-20）

背景：东方财富目录接口持续失效，在线同步的「标的发现」环节不可用。本文全部结论来自本机实测；**未实测的条目均已标注**，不以传闻下结论。

测试环境：隔离 venv（Python 3.13，baostock 0.9.30）。测试方法说明见文末。

## 一、结论速览

| 结论 | 关键依据 |
|---|---|
| **东财不是整体解封，是 `clist` 被针对性封禁** | 8 个节点目录接口全断，但同域名 `stock/get` 正常返回 200 |
| **东财日线接口属于「间歇可用」，不可作为依赖** | 同一批请求里一次 200、一次 `RemoteDisconnected` |
| **腾讯 `newfqkline` 稳定，且单位换算与现在代码一致** | 用新浪作第三方独立验证通过（见第四节） |
| **baostock 可用，适合做「标的目录 + 交易日历 + 个股/指数历史」** | 无需注册、含退市股、有无幸存者偏差的时点成分 |
| **baostock 的 ETF 历史只有约 8 个月，不能用于 ETF** | 无论复权参数怎么设，ETF 一律只回溯到 2026-01-05 |
| **不建议回头走 pytdx / TDX TCP** | 项目 3 天前刚因「公共服务器不再稳定响应」移除该通道 |

## 四、腾讯通道：深度实测 + 第三方验证

一条坏消息和一条好消息。

### 好消息：单位换算被独立源验证是对的

用新浪作为第三方，对同一批交易日做逐值比对：

| 标的 | 交易 | 腾讯 | 新浪 | 比值 |
|---|---|---|---|---|
| sh600000 沪个股 | 2026-09-18 | vol=517593.00 | vol=51759299 | **100.00** |
| sz159915 深 ETF | 2026-09-18 | vol=18523198.00 | vol=1852319819 | **100.00** |
| sh000001 沪指数 | 2026-09-18 | vol=485712507.00 | vol=48571250700 | **100.00** |

即腾讯（除科创板外）给的是**手**，与 baostock / 新浪的**股**正好差 100 倍。`online_market_sync.py:703` 只对 688/689 做 ÷100、其余原样，**与实测一致**，H1 那次修复方向正确。

### 坏消息：腾讯**忽略请求的起始日期**

每次请求都返回**截至窗口末尾的最近 N 根**，而不是窗口内的那些：

```
请求 sh600000 2026 年窗口（2026-01-01 ~ 2026-12-31）
  → 返回 640 根，区间却是 2024-01-29 ~ 2026-09-18
请求 sh600000 2005 年窗口
  → 返回 640 根，区间 2003-05-14 ~ 2005-12-30
```

同时**单次上限约 2000 根**（n=2000 正常，3200 起返回 `param error` 且 data 为空 list）。

⇒ 想拿长历史必须「按锚点往回倒」。现有实现 `online_market_sync.py:644-652` 恰好是**按自然年循环 + 每次 640**，天然符合这个行为，而且 `:708` 有 `(date >= start) & (date <= end)` 兜底裁剪 —— **现有代码是对的**，不用改。只是中间帧会有重复日期（靠 upsert 去重），效率上偏浪费，属于可接受范围。

### 其他注意点

- **指数收盘价只有 2 位小数**：腾讯 `3891.60` vs baostock / 新浪 `3891.6010`。3971 个重叠交易日里只有 421 天完全相等，差异全部来自腾讯的舍入。指数相关的精细计算要注意这一点。
- ETF / 个股历史深度足够：个股可回溯到 2003 年、ETF 到 2011 年、指数到 2003 年（逐年请求可达）。

## 五、baostock：详细实测

### 5.1 可用性与覆盖

```
login            → ec=0 success，0.58s
query_all_stock(2026-09-18) → 7401 条，25.6s
  sh.60 1702 / sz.00 1494 / sz.30 1407 / sz.15 738(深ETF)
  sh.68  618 / sh.51  446(沪ETF) / sz.39 286(指数)
  sh.56  261 / sh.00  221(指数) / sh.58 149
```

**含「时点成分」，这对回测很重要**：

| 查询日 | 返回标的数 |
|---|---|
| 2019-01-02 | 4136 |
| 2023-01-03 | 5447 |
| 2026-09-18 | 7401 |

数量随年份增长、且 2019 年列表里没有后来的 ETF 前缀 ⇒ 返回的是**当日在市标的**而非「活到今天」的标的，**可免除幸存者偏差**。这是多数免费源不具备的优点。

**不含北交所**（`bj.` 前缀零命中，与本地 `.day` 导入的既有限制一致）。

### 5.2 吞吐（严格串行）

| 场景 | 数据量 | 耗时 |
|---|---|---|
| 单只 1 年 | 240 根 | 中位 **0.40s** |
| 单只 5 年 | 1454 根 | 5.65 – 8.37s |
| 单只全历史 | 6511 – 8657 根 | 18.4 – 22.5s |
| 混合 8 只 × 1 年 | 1794 行 | 成功 8/8，`ec=0` |

**外推**：全市场约 5000 只 × 近 1 年 ≈ **33 分钟**；× 近 5 年 ≈ **45 分钟**。作为离线批跑完全可接受。

### 5.3 字段与单位

返回：`date, code, open, high, low, close, preclose, volume, amount, turn, tradestatus, pctChg, isST`

- **成交量单位是「股」**：`amount / volume = 9.080 ≈ close 9.07`，amount 单位是元。接入现有「手」口径**必须整除 100**。
- **含 `tradestatus` 停牌标记**（比东财/腾讯多出来的有用字段）。
- **除权基准正确**：2026-07-16 浦发 `preclose=8.89`、前日 `close=9.31`（差 0.42 即每股派息），`pctChg` 以 8.89 为基准。`query_adjust_factor` 交叉确认该日确有除权事件 —— 属正确行为。
  ⇒ 注意：**`preclose` 是除权参考价，不可当作项目意义上的「未复权昨收」**，`close` 才是真实成交价。
- 自洽性抽查 57 根，仅 1 处不符，即上述除权日。
- 复权支持：`adjustflag` 1/2/3 + `query_adjust_factor`（两者互为验证）。

### 5.4 ⚠️ 致命短板：ETF 历史只有约 8 个月

```
ETF 159915 请求近 5 年  → 174 行  首=2026-01-05
ETF 159915 请求 2025 全年 →   0 行
ETF 510300 请求近 5 年  → 174 行  首=2026-01-05
个股 600519 请求近 5 年  → 1454 行 首=2020-09-21
指数 000001 请求近 5 年  → 1454 行 首=2020-09-21
```

与 `adjustflag` 取值无关（1/2/3 都是这 174 行）。ETF 专用接口 `query_daily_history_k_ETF` 的真实签名是 `(date='')` —— 只支持「取某一天的全市场 ETF」，2015-09-20 / 2020-01-10 全部返回 0 行，说明**不是调用姿势问题，是数据本身只从 2026 年开始收录**。

⇒ **凡涉及 ETF 历史回测，baostock 不可用，必须走腾讯。**

## 六、若接入 baostock 必须遵守的工程约束

1. **绝对不能并发**（你提的这个点是对的，但风险比想象更大）
   - 源码级原因：`SocketUtil` 是**单例**，socket 挂在全局 `context.default_socket`；`send_msg()` 无锁地 `send` 后循环 `recv(8192)` 直到读到 `<![CDATA[]]>` 结束符。多线程请求/响应会在同一条 TCP 连接上交错 —— 轻则数据错位，重则等不到结束符而永久阻塞。
   - 今天两次「>6 分钟无响应」都发生在有第二个进程同时连接的时候，与此机制吻合。

2. **必须外加硬超时**。`SocketUtil.connect()` 创建的 socket **没有设置任何超时**，服务端不响应就是无限期挂住；实测 `socket.setdefaulttimeout(30)` 也救不回来 ⇒ 建议把查询包进子进程/线程，外层硬超时 + 重试。

3. **volume ÷ 100** 转成「手」，与现有口径对齐。

4. **`preclose` 是除权参考价**，别当未复权昨收用。

5. **ETF 历史缺失**要显式标记来源，否则会静默产生「看着完整、实则只有 8 个月」的脏数据。

6. **无北交所**。

7. 更新节奏为收盘后约 1 小时，**不适合盘中实时**。

## 七、建议：按用途分层，而不是整体替换

| 用途 | 推荐方案 | 理由 |
|---|---|---|
| **全市场标的目录 + 交易日历** | **baostock** `query_all_stock` / `query_trade_dates` | 精准补上东财 clist 被封的缺口；每天一次即可，串行无压力 |
| **个股 / 指数 / ETF 日线** | **腾讯 `newfqkline`（主）** | 又快又稳、自带 amount、ETF 历史完整、支持并发；现有代码已经是对的 |
| **个股 / 指数历史的校验 & 兜底** | **baostock** | 提供退市标的、停牌标记、换手率等额外字段，也用于对拍发现异常 |
| **日频增量辅助** | 东财（可重试 + 降级） | 当前属于「时好时坏」，只能作为容错路径 |

**不建议**：引入 pytdx / AkShare 作为主源（前者的稳定性问题项目有历史记录，后者的底层就是这次出问题的东财）。

如果只做一件事，我建议是：**把 baostock 的 `query_all_stock` 接进来当目录源**。它能立刻解掉「在线同步跑不起来」这个死结，改动面最小，且串行调用在这个频率下完全不是瓶颈。

## 九、落地情况（2026-09-20 当日已实施）

第七节的建议已按「分层」落地，未做整体替换。

| 用途 | 落地内容 | 位置 |
|---|---|---|
| **日线主源** | 腾讯 `newfqkline` 提到首位，东财降为容错 | `online_market_sync.py::_fetch_with_retries` 的 `source_requests` 顺序 |
| **标的目录** | 新增 baostock 目录源并置于首位，东财 `clist` 兜底 | `adapters/baostock_catalog.py` + `_fetch_catalog_frame` |
| **可选依赖** | baostock 放进 `catalog` extra，未安装时自动回退 | `pyproject.toml`、`Dockerfile`（`'.[catalog]'`） |

### 关键设计

- **子进程隔离**：每次目录查询启一个短命子进程跑完「登录 → 取最近交易日 → 查询 → 登出」，硬超时由 `subprocess.run(timeout=...)` 保证。这是第六节第 1、2 点的直接后果——baostock 的 socket 是全局单例且没有超时，实测一次卡死挂了 4 分多钟才被手动杀掉。**不要把它搬回主进程。**
- **自动定位交易日**：`query_all_stock(day=None)` 取「当天」，周末/节假日返回 0 行（2026-09-20 周日实测就是空）。子进程先用 `query_trade_dates` 找最近交易日再查。
- **超时按目录的量级给**：实测一次全市场查询 26~51 秒，所以默认 150 秒，且与单根 K 线的 `config.timeout` 取较大值。用 30 秒会变成「每次都超时、每次都静默降级」。
- **一次查询服务多个品种**：baostock 一次返回全市场，同一份帧复用于股票与 ETF 的选择逻辑，不像东财要按品种各拉一次。

### 实测结果（本机，2026-09-20）

```
fetch_all_securities()            -> 7401 行，51.3s（含自动定位交易日）
discover_instruments(stock)       -> baostock_stock_list  5341 只，33.0s
discover_instruments(stock+fund)  -> baostock_mixed_list  7014 只，38.2s
腾讯日线 sh600000 2026-09-18      -> volume 517593 手（对得上新浪 51759299 股 ÷ 100）
```

### 未做的部分

- **交易日历**：`query_trade_dates` 目前只用于定位目录的交易日，没有单独对外提供日历接口。
- **个股历史的 baostock 兜底**：第七节建议用它做个股/指数历史的校验与兜底，本次未做——日线主源腾讯实测稳定，且 baostock 单次 20~40 秒的吞吐扛不住全市场日线。
- **北交所**：baostock 目录里的 `bj.*` 被显式过滤掉，行情库仍是 SH/SZ 两市。
