## 一、选取原则（四条门槛，缺一不进）

1. **与定位一致**：我们是「日线研究工具」，不是盯盘终端、不碰实盘。任何需要分钟数据、7×24 常驻、或偏向实盘记账的功能，一律不进。
2. **能被证伪**：这是我们的核心卖点。新增的展示型功能必须能回答「凭什么信它」——不能证伪的漂亮图表会稀释这件事。
3. **不引入新数据源**：现在只有日线（东财/腾讯/baostock）。需要龙虎榜、财务四表、概念行业、fuyao/ths 的，先别做。
4. **优先「把已算出来的东西变成看得见的证据」**，而不是对齐别人的功能表。前者便宜且强化卖点，后者贵且稀释定位。

## 三、P0 详细

### 3.1 策略追踪 ★ 价值最高，建议优先排期

#### 它是什么

用户把一个策略（选股规则 + 组合参数）**保存并"上线"**（上线日 = 今天），系统此后每个交易日收盘后用最新行情重算一次，把**上线前的回测段**和**上线后的模拟观察段**并排展示。可以同时创建多个策略，在总览表里横向比较。

对应 同类产品 的「策略追踪」。术语上我们沿用「上线日 / 上线前 / 上线后」，内部语义是**研究段 / 观察段**——守住"研究工具、不碰实盘"的定位。

#### 为什么它对我们特别有价值（这才是重点）

不是因为"多了个功能"，而是它填了一个根本性的空白：

**我们目前所有能力都是一次性的。** 挖条件 → 回测 → 看结果 → 结束。它回答的是"历史上这套东西好不好"。而策略追踪回答的是另一个问题：**从今天起，它还灵不灵？**

我们花了大力气做置换门槛、BH-FDR、因果无前视适配，全部是为了提高「结论在未来也成立」的概率。但产品里**没有任何东西去验证这个概率**。策略追踪就是那个验证器——它是整个可信度体系的闭环。

另外两条：

- **它是唯一的留存机制。** 现在这个产品用完即走，用户没有任何理由明天再来。追踪数据随时间积累、越用越值钱，这是留存的唯一抓手。
- **它是内容金矿。** 跑满一年就能回答一个别人答不了的问题：**"通过置换检验的策略，一年后真的跑赢了吗？"** 这比任何功能都更能证明我们在做什么。

#### 与 同类产品 版的四个关键差异（不能照搬）

| 维度 | 同类产品 | 我们应该这样做 | 理由 |
| :--- | :--- | :--- | :--- |
| 策略内容 | 参数化的策略类型（网格/定投/资产配置/轮动） | **规则组 RuleGroup + 组合参数** | 我们的策略是"选什么、什么时候进出" |
| 改参数 | 追踪页可直接改参数并"保存并重算" | **不允许修改已上线策略的规则** | 改了就不是样本外了。要改 → 新开一个追踪。这是硬约束 |
| 核心看点 | 收益曲线、交易记录 | **样本外衰减 + 对照基准** | 见下 |
| 评分/标签 | 有综合评分 | **不做综合评分** | 不可证伪，见 §4.1 |

**核心看点应该是可证伪的两件事，而不是收益曲线本身：**

1. **衰减比** = 观察段指标 / 研究段指标（年化、夏普各算一个）。只展示，不给硬性判定阈值。
2. **观察段 vs 基准** = 观察段内策略收益 vs 同期买入持有基准。这是硬的、可证伪的对照。

多个策略并排时，还能给出**整体衰减分布**：「我追踪的 N 个策略里，M 个在样本外衰减超过一半」。这个数字市面上没人有。

#### 落地建议

- 入口：策略库每行加「开始追踪」（上线日 = 下一个交易日，按本地交易日历对齐）
- 新页面「策略追踪」：

  - 详情：分段净值曲线（上线日竖线切分）+ 交易明细 + 当前持仓 + 与基准对比
- 数据：
  - `saved_strategies` 扩 4 列：`tracking_status`（off/active）、`launched_at`、`last_tracked_date`、`last_error`。研究段绩效存在 `summary_json.tracking_research` 里，**上线即冻结**
  - 新增 `strategy_tracking`（主键 strategy_id + trade_date）：每日净值/现金/持仓数/基准值/回撤
- 重算：**全量重跑**（每日一次，串行），从报告中按上线日截断。失败只写 `last_error` 并**停在旧日期**
- 调度：`StrategyTrackingScheduler` 每 15 分钟检查一次，条件是有 active 策略 + **没有活跃的数据任务**（顺序反了会拿旧数据算出一份看着正常的结果）+ 最新交易日落后于 `last_tracked_date`
- 完整版才做：暂停/恢复、跨策略的衰减分布报告（当前只有总览表顶部一句话）

#### 开工前必须先确认的三件事

1. ~~`replay_service` 能否吃到组合回测策略~~ —— **已确认：能。**（`replay_service.py:75` 就是组合回测引擎）剩下的是把"候选来源"从排行榜换成我们持久化的策略表，成本的最大变量已消除。
2. ~~**重算粒度**~~ —— **已确认：可以只算新增的一天。** 原判断（"持仓连续，所以必须从上线日重跑"）被推翻：`SimulationCheckpoint` 把持仓、挂单、冷却期、回撤、已输出行全部序列化，续跑产出的报告与全量跑一致。所以每日成本 ≈ 一天，且不随追踪时长线性增长。剩下的成本大头是 contexts 准备（指标计算），靠 `IndicatorCache` 摊掉。
3. ~~**规则冻结的存储形式**~~ —— **已确认：无需新迁移。** `saved_strategies.request_json` 存的是 `PortfolioBacktestRequest.model_dump(mode="json")` 全量快照（含 RuleGroup），保存时已把相对日期固化成绝对日期。

#### 已知的坑（同类产品 都踩过，直接抄答案）

- 上线日要**按交易日历对齐**到首个有效交易日，不是按自然日
- 追踪所需行情缺失时**先自动补齐**再重算；补失败要保留失败状态并提示原因，不能静默算出一个空的"成功"
- 重算**必须在数据自动更新之后**（同类产品 是 18:30 更新、18:40 追踪）；顺序反了会算出空结果
- 追踪期间标的退市/停牌要标记，否则幸存者偏差会污染结论

### 3.2 滚动样本外（walk-forward）验证

条件研究现在是 60/20/20 **单次切分**，结果依赖这一次怎么切。改成多窗口滚动（例如 5 个滚动窗口），报告每个窗口的一致性。复用现有切分逻辑。

这是 memory 里已记录的已知缺口，也是"防过拟合"最直接的补强。

### 3.3 参数敏感性分析

挖出的阈值，看它在邻域内稳不稳（阈值上下浮动 ±10/20%，收益曲面是否悬崖）。产出是一张热力图——**是"这条结论靠不靠谱"最直观的证据**。条件研究和波段研究两处都能用。

**若想先做一个小的热身再动策略追踪，它是成本最低的选择。**

### 3.4 挖掘结果的相关性去重

TSP 有，我们 `condition_research` 没有（`strategy_discovery` 只有 trade-behavior 去重）。对候选条件的命中序列算相关，剔除 |ρ| 过高的同义条件。工作量低。

不做的话，候选表里会出现五条本质相同、只是阈值差一点的条件，看起来像五个发现。

### 3.5 单指标/因子检验页

IC、ICIR、分层收益、多空组合——`condition_research/ranking.py` 已经在算了，只是藏在"排序推荐"里。抽出来做成独立页面，收益是**我们最稀缺的能力终于有了一个正门**。

### 3.6 累计试验次数校正 ★ → 已于 2026-09-22 上线，见 §9.15

**它是什么**：跨运行「取最好」的偏差。单次研究里并排检验了几千个条件这件事，max-T 置换
已经校正过了；没被覆盖的是**你跑了 K 轮研究，最后记住的是 K 轮里最好的那个**。跑得越多，
同一个 p 值越不值钱，这一层只能靠记账来补。

### 3.7 最小跟踪记录长度（MinTRL）→ 已于 2026-09-22 上线，见 §9.14

MinTRL 是 DSR 的反解：给定观察到的 Sharpe、偏度、峰度，还要多少样本才能在 95% 下拒绝
"真实 Sharpe = 0"。公式成熟，实现半天。

**替换掉什么**：`portfolio_backtest/tracking.py::MIN_OBSERVATION_BARS` 现在是硬编码的 20 交易日，
"样本过短"这个标注说不出口理由。换成 MinTRL 之后，同一个判断变成
"以你现在的 Sharpe 0.6、偏度 −0.4，需要 14 个月才能谈显著性；你只有 3 个月"。

收益序列我们本来就有，几乎不需要新的数据通路。

## 四、P1 详细

### 4.0 回测历史对比 ★ P1 里性价比最高 → 已于 2026-09-21 上线，见 §九 9.7

**现状**：`backtest_history` 已经存了 5 种类型（`single_stock` / `portfolio` / `strategy_fitness` / `condition_research` / `swing_research`），但 `BacktestHistoryPanel.vue` 只有**刷新 / 载入 / 删除**三个动作，**没有任何对比能力**。每个页面各看各的历史。

**为什么值得做**：研究这件事本身就是"反复做实验 + 比较实验"。现在做完 5 次条件研究、5 次组合回测，没有任何地方能把它们摆在一起看。这是工作流的硬缺口。

**我们能做得比 同类产品 更强**：它只能勾选**同类型**两条记录对比（都是组合轮动）；我们的历史是**跨类型统一存储**的，所以可以做**跨类型对比**——比如"条件研究挖出的条件 A" vs "波段研究的结论 B"，在组合回测上谁更好。这个是别人没有的。

**落地**：数据已经够了（`result_json` 存了完整结果，含净值曲线），主要工作是取数 + 归一化叠绘 + 指标并排表。前端无图表库，叠绘要手写 SVG（可参考 `MarketCandlestickChart.vue`）。

**注意**：不同研究类型的"净值曲线"语义不同（条件研究是候选的表现，组合回测是资金曲线）。跨类型对比时要明确标注口径，别让用户误以为是同一件事。

### 4.1 标的检验台（源自 同类产品「ETF 分析」，需改造）★ 已于 2026-09-21 上线，见 §九 9.8

#### 原功能是什么

ETF 分析 = 单日横截面列表（每个标的评分 + 标签 + 指标值）+ 指标筛选 + 区间时间轴 + 单标的全仓回测（K 线 + 买卖点 + 资金曲线）+ 多标的走势对比 + 策略优选。

#### 我们已有 vs 缺

| ETF 分析的能力 | 我们现状 |
| :--- | :--- |
| 单日横截面列表 + 指标值 | **有**（公式选股页） |
| 指标筛选（AND/OR、上穿下穿、指标对指标） | **有**，且更强（条件研究同源） |
| 策略优选 | **有**，且更强（策略实验室 + 适配性评估） |
| K 线 + 副图 + 买卖点 | **组件已有**（`MarketCandlestickChart.vue`，387 行手写 SVG，含 MA/MACD/RSI/成交量/公式面板） |
| 单标的全仓回测 | 页面已删，**引擎还在**（`backtest/service.py|models.py|engine.py` 被条件研究与适配复用，不能删） |
| 综合评分 / 标签 | 无 |
| 区间时间轴（分数随日期变化） | 无 |
| 多标的走势对比 | 无 |

**真正的增量只有三块**：时间轴、单标的回测页（复活）、多标的对比。

#### 必须改造的一点：不做综合评分

"综合评分"是**不可证伪**的——权重谁定的？凭什么？同类产品 和 TSP 的评分都是自定口径，抄过来等于把我们的可信度押在别人的定义上，直接违反门槛 2。

**改成「标的检验台」**：选一个标的 → 看它在我们已有指标上的全历史取值（时间轴）→ 叠加它的信号与回测结果 → 关键是展示**「这个标的在通过置换检验的条件上表现如何」**，而不是一个拍脑袋的综合分。这样它才是我们的东西。

命名也不该叫「ETF 分析」——我们支持股票 / ETF / 指数 / 债券，叫 ETF 是错的。

#### 为什么是 P1 不是 P0

它偏**便利性**（看单标的更顺手），不直接强化可信度卖点；而 P0 那几条都是。价值真实，但不优先。

零成交日、与全市场交易日的对齐情况。修复有人按的按钮，但没有自动修复——判断权留在人手里。

### 4.8 涨跌停不可成交约束

果仁网被反复提到的优势是"内置了非常真实的 A 股撮合逻辑（自动处理分红、停牌、**涨跌停买不进**）"，
第三方评测把它列为核心卖点。

**我们的现状**：`portfolio_backtest/models.py:72-75` 的成本模型齐
（`commission / min_commission / stamp_tax / slippage`），但**没有涨跌停约束**——
涨停日的买入、跌停日的卖出在回测里都成交了。

**影响是单向的**：条件研究挑出来的往往是强势股（刚启动、正在冲），这类标的恰好最容易撞涨停，
所以缺这条约束会**系统性高估**结果，不是随机误差。

**待拍**：默认关（报告显式标注"未考虑涨跌停不可成交"）还是默认开（成交率下降、样本变少）。
倾向默认关 + 显式标注，因为我们是研究工具，且标注本身就是"可证伪"的一部分。

#### 2026-09-22 重新评估：从 P1 降到 P2

上面「不可成交」这四个字是错的，用户当场指出：**涨跌停时照样能成交**。真实机制是
**方向不对称**：

| | 买入 | 卖出 |
|---|---|---|
| **涨停（封住）** | 难：排在买一队列，要等有人卖 | 容易：直接砸给买一 |
| **跌停（封住）** | 容易：有人在卖一挂着等你 | 难：排在卖一队列 |

四格里只有「涨停买入」「跌停卖出」两格是难的，而这两格恰好是回测最爱占便宜的方向——
所以「单向高估」这个结论保留。但把它实现成「涨跌停日一律不成交」是错的：

1. 禁掉涨停卖出、跌停买入 = 在**最容易成交**的方向上假装成交不了，引入的是反向偏差，
   而且比原偏差更难被发现；
2. 大量「盘中触及涨停但未封死」的日子收盘价挂在涨停价、全天却成交活跃，按收盘价撮合
   其实买得进，硬禁会一起错杀。

结论：**严重性还在，但规则拍不准**——而按我们的排序标准（错误可见性），「拍错了引入一个
静默的新偏差」比「暂时没修一个已知偏差」更糟。所以降级，并拆成两步：

- **23a 暴露度报告**（只读、无争议、快）：回测结果里统计有多少笔买入发生在涨停日、多少笔
  卖出发生在跌停日，以及这些笔贡献了多少收益。回测历史里已有成交日期与价格，跟
  `daily_bars` 一 join 就算得出，不跑新回测。
- **23b 撮合约束**：拿到 23a 的数字再决定。暴露度 <1% 直接降 P3；>5% 再做，且做成
  **买入侧受限、卖出侧不限**的方向性约束。

同批已修掉一处会误导人的文案：`factor_attribution/service.py` 原写「被拒单（资金不足或**涨停**
等）」，但代码里 `rejected` 只来自成交记录标记，**没有任何涨停拒单逻辑**；资金不足也不是拒单，
而是把委托量缩到买得起，`size` 为 0 时压根不记这一笔。现文案改为「N 笔委托被标为未成交」。

## 五、P2 — 谨慎，先别动

- **PBO / CSCV（#24，组合式交叉验证）**：与已交付的滚动复验（#2，序列式 walk-forward）**部分重叠**。
  PBO 用组合对称交叉验证估计"样本内冠军在样本外落到中位数以下的频率"，回答的是
  "我的挑选流程本身有多过拟合"，而 walk-forward 回答的是"这条规则换个时期还行不行"。
  价值真实但增量有限，且要先把 #20 的有效 N 口径定下来才有意义。排在 #20 之后。
- **AI 对话助手**：2026 年它是流量，也是大工程。若做，**必须学 TSP 的"工具足迹卡（参数与耗时可展开核对）"**——让 AI 每次取数可核对。一个黑箱 AI 助手会砸我们自己的招牌。
- **市场环境 / 情绪周期**：需要概念、行业、连板数据，我们只有日线；且偏择时，稀释"严谨选股"定位。
- **扩展数据插件化**：前提是先有第三方数据。
- **回测报告增强**：周期收益分布（月度/年度）、持仓变化时间线、每日收益柱状图。价值真实但偏"看得更细"，不强化可信度。等 P0/P1 做完了再回来取。
- **策略组合**（同类产品 §5.3，多策略按权重合并运行）：契合我们"分散 = 降低对单一规则的过拟合风险"的关切，但**强依赖 #1 的策略持久化**（得先有"已保存策略"才能组合）。**等 #1 做完再评估，现在排不了。**
- **新手引导 / 首次使用流程**：我们的上手门槛比 同类产品 更高（要理解指标、条件研究、置换检验）。这不是核心功能，但**对外（开源或发内容）之前必须有**。

### 9.14 最小跟踪记录长度 MinTRL（#21，2026-09-22 上线）

把策略追踪里那个拍出来的「观察段不到 20 个交易日」换成能说出理由的判断：
**按你目前的表现，还要多少个交易日才能在 95% 把握下说它真的在赚钱。**

公式来自 Bailey & López de Prado 的 Deflated Sharpe Ratio 一脉，实现落在新建的
`aquest/statistics/deflated.py`（#20 的期望最优 Sharpe 也会放这里——两件事同出一源，
分开写迟早长出两份不一致的常数）。

**量级（实测，日波动 1%）**：年化夏普 0.3 → 约 30 年；0.6 → 约 7.5 年；1.0 → 约 2.7 年；
1.5 → 约 1.2 年。这个数字本身就是产品信息——**大多数策略的观察段都不够长**，而且不是
差一点，是差一个数量级。

**三条口径（改动前定死）**：

1. **MinTRL 通常远大于观察段，那是进度不是错误。** 所以界面上它是中性提示（和"数据太少"
   那条同样的样式），文案写「需要 N 个交易日（约 X 年）；已观察 M 个，还差 D 个」，
   不写成警告。写成红色警告会导致每条策略都挂着警告，信息量归零。
2. **算不出来必须是 `null` 而不是 0 或无穷。** 三个退出点：平均收益不为正（谈"显著为正"
   没有对象）、零波动（Sharpe 无定义）、收益率不足 20 个（三四阶矩估不准，给个数会让人
   以为算准了）。`null` 一律不显示提示。
3. **进公式的是日频 Sharpe 不是年化。** 年化是展示层换算，直接代进去会差 √252 倍——
   这个错我自己在测试里连踩两次，两次的表现都是"数值离谱地小"。

**撞到的一个洞察（写在这里省得重新推）**：随机序列下 MinTRL 的断言会跟着抖，原因是
「让样本均值估计稳定的样本量」恰好就是 MinTRL 要求的量——二者是同一个条件的两面。
所以测试里用的是**确定性序列**（交替 +1% / −0.9%），不是随机序列。

### 9.15 累计试验次数校正（#20，2026-09-22 上线）

把「你跑了 K 轮研究，最后记住的是 K 轮里最好的那个」这层偏差补上。

**先说清楚它不校正什么**：单次研究里并排检验了几千个条件这件事，`mining.py` 的 max-T 置换
已经完整覆盖了——它把标签打乱、给**同一个候选池**重新打分，看纯运气能把最好的那个 lift
推到多高。置换天生处理任意相关结构，所以不需要再估什么「有效独立试验数」。

（这一点是实测之后才确认的，走过弯路：原本打算按相关结构折算有效 N。用真实日线构造候选池
算完整相关矩阵，得到 ΣΣρ = 8.2 而 N = 1248，代进 `N_eff = N²/ΣΣρ` 给出的数比 N 还大——
因为候选里 gte/lte 成对出现、正负相抵，而且**那个公式是均值方差的等效样本量，我们校正的
对象是最大值**，两者不是一回事。结论：单次运行内的相关结构交给置换，不要另估 N_eff。）

**记账单位是「独立数据轮」，不是条件数，也不是研究次数。** 关键判据：

- 换参数在同一段数据上重跑，**不增加撞好运的机会**。候选池一样、样本一样、置换用固定种子，
  挖出来的东西一模一样——重复 9 次和跑 1 次，统计上是同一轮。
- 日期区间重叠过半（Jaccard ≥ 0.5）视为同一轮，且重叠是传递的。

**实测本地库（2026-09-22 读副本，只读）**：9 次条件研究的区间**全部**是 2021-09-11~2026-09-11，
4 个数据指纹里有 3 个是重复跑。按轮数记 K = 1，按次数记会是 9。差别有多大：

| 原始 p | 按轮数 K=1 | 按次数 K=9 |
|---|---|---|
| 0.01 | 0.010 显著 | 0.087 **不显著** |
| 0.03 | 0.030 显著 | 0.240 **不显著** |
| 0.045 | 0.045 显著 | 0.339 **不显著** |

粗暴按次数记账会把 p=0.01 也误判成不显著——**过度惩罚和漏校正一样是错的**。

**校正公式**（Šidák）：`p_adj = 1 − (1 − p)^K`，K=1 时恒等，所以只跑过一次研究的用户
结果完全不变。这是对的：没有跨运行的选择偏差需要校正。

**顺带挖出来的一个更有价值的信息**：`repeated_studies = 研究次数 − 轮数`。它不改变 p 值，
但「你在同一段行情上挖了 9 次」是最直接的过拟合信号，界面上明说。

**落点**：
- 新表 `condition_research_trials`（history_id / 数据指纹 / 区间 / 本次检验条件数），
  与 `backtest_history` 同步截断；
- `condition_research/trial_ledger.py`：轮数聚类、Šidák 校正、累计条件数；
- 报告新增 `trials` 字段；候选的 `mining` 新增 `adjusted_pvalue`、`trial_count`，
  **原始 `permutation_pvalue` 保留**，判定改用校正后的值。

**两条口径**：① 没做置换检验时三个字段一起是 `None`，不能凭空编一个"已校正"；
② 台账读写失败只警告（回退到 K=1），审计信息不能成为研究失败的原因。

### 9.16 行情数据健康检查 + 一键重下（#22，2026-09-22 上线）

把所有下游结论依赖的那个前提——「行情没有洞」——显式化。以前它从未被验证过，
缺 bar、长期停牌被当成价格不变、复权断点、异常价都是**静默**的，越往下游越看不出来。

**六项检查**：行情缺口、连续缺失段、价格结构错误（高 < 低、收盘越界、非正价格）、
异常跳变（超板块涨跌停幅度 + 1 个百分点容差）、零成交日、数据陈旧。

**三条口径（改任何一条都要同步改 `health.py` 的模块注释）**：

1. **交易日是从数据里选出来的，取峰值不取中位数。** 某天有 bar 的标的数达到峰值的
   50% 才算交易日。方向是刻意的：多算一个交易日只会多报一处缺口（误报，看得见），
   少算一个交易日则会把当天所有标的的缺口**掩盖**（漏报，看不见）。中位数方案在验证
   时被自己推翻——标的数少的库里，大范围缺失会把中位数一起拉低，于是缺失本身就变成了
   「这天不算交易日」，自己把自己藏起来。
2. **缺口只在标的自己的首末日期之间数。** 上市前与退市后都不算缺口，否则每只票都会被
   判成"缺了几年"；退市/漏同步单独走 `stale`。
3. **只报不修，修由人显式触发。** 列表里的「修复」按钮要过一次确认弹窗。

**一键修复 = 先删后下，顺序不能反**，两条硬理由：在线行写不进已有本地行的位置（本地行
永远压过在线行）；`full_history` 只补已有区间**之外**的缺口，不先删就覆盖不到中间那段。

代价是删掉后在线拉不到的标的（退市）会变空，所以：结果里单独列 `empty_after_repair`，
前端点名显示；一次最多修 500 只，`truncated` 会写明还有更多没修。

**接口与落点**：`market_data/health.py`（报告模型与阈值）+ `store_health.py`（SQL），
`POST /market-data/health/check`、`POST /market-data/health/repair`；
`MarketSyncConfig.codes` 支持只重下指定标的（顺便不覆盖全量证券列表指纹）。
两个任务都登记进 `MARKET_SYNC_JOB_DESCRIPTIONS`，所以能轮询、能取消、受同一道
「同时只允许一个行情任务」的闸门约束。前端落在本地行情页（不新增页面）。

**实测**：600 万行（5000 只 × 1200 天）全量体检约 **10 秒**——所以必须走任务而不是同步
返回，同步会把请求线程按死。15 个后端单测 + 4 个集成测试 + 4 个前端测试。

### 9.13 用户手册 + 页内功能说明（#25，2026-09-22 上线）

13 个页面每个都多了「这个功能怎么用」区块，同一份内容自动生成 `docs/user-manual.md`。

**关键是这两边不许各写一份**：手册和界面说明一旦分开维护，半年之内必然一处改了另一处没改，
而没改的那一边往往正是被别人引以为准的那一边。所以内容只在
`web-ui/src/data/pageGuides.json` 里存在一次：

- 页面上的 `PageGuide` 组件读它渲染说明区块（默认收起，展开状态按页面分别记在 localStorage）；
- `scripts/generate_user_manual.py` 读它拼出 `docs/user-manual.md`（也可 `npm run gen:manual`）；
- 一条守卫测试盯着三件事：每个页面都挂了说明、说明里的路由与 `App.vue` 的分支一致、
  每个页面都手写齐了全部 13 条导航链接。

**内容上刻意做的事**：每条说明都写「它不能回答什么」和「口径提醒」，而不只写「能做什么」。
这和产品的可信度立场是同一件事——一份通篇"可以做"的手册，跟不可证伪的营销页没有区别。
组合回测那条直接写明"未考虑涨跌停不可成交"，把它当作已知缺陷摊开，而不是藏在文档外面。

### 9.12 回测闭环（#11，2026-09-22 上线）

原话是「结果 → 保存候选 → 一键载入复测。我们有回填，可以做得更顺」。做下来发现"不顺"的
根源不是缺某个按钮，而是**历史记录的「加载」多数页面只把结果塞回屏幕、不还原输入**——想
微调一点再跑一遍，只能凭记忆重填整张表单。

所以交付的形态是：**加载历史 = 表单回到当时那个样子**，外加候选库补上回到研究的入口。
纯前端：历史记录里本来就存着完整 request，不需要新的服务端接口。

**口径（改动前就定死的，别改）**：

1. **加载 ≠ 重跑。** 历史存的是"当时跑过什么"，页面上的结果仍是旧的那一版。提示统一写成
   「已还原…请确认后重新运行」，不许再写「已加载」让人以为又跑了一次。
2. **漏字段是最容易犯也最难发现的错，用测试收口。** 每个页面一条"还原完整性"用例：构造
   一份**每个字段都偏离默认值**的 request，加载后逐个字段断言表单。将来表单加字段而还原
   逻辑忘同步，测试会红。
3. **自定义公式必须先解析再回填规则。** `parseCustomFormula` 会重置买卖规则与排序值，
   顺序反了这一份就白还原（组合回测页原来就踩过一次，这次照搬教训）。
4. **date_mode 必须和绝对日期一起还原。** 只还原日期不还原模式，下拉显示「最近五年」而
   实际按自定义区间跑。
5. **键用完立即清。** 还原靠 sessionStorage（`aquest.condition-research.restore`），
   读完就删——刷新页面不该再还原一次，否则用户刚改过的东西会被悄悄覆盖。

**这次改动到哪些页面**：因子检验（原先只还原 4 个字段）、因子归因（补 3 个）、策略适配性
（原先完全不还原）、组合回测（原先完全不还原）、候选库（新增「载入复测」）、条件研究
（新增接收端，复用它已有的 `applyStoredRequest`）。

**明确不做**：

- **不让非条件研究类型进候选库。** `candidate_library/service.py::import_candidates` 只认
  `condition_research`，这不是缺陷：候选条目带一份证据快照（§9.10），lift / 置换 p 值来自
  条件研究的挖掘口径，波段研究、因子检验、适配性的产物没有这些量。硬塞进去要么留空（造出
  没有证据的条目），要么套用不相干的指标（不可证伪）。"候选 = 可验证的买卖条件"才是它的价值。
- **不加「历史 → 重跑」的后端端点。** 还原是纯前端的事，加服务端接口只会多一条维护路径。
- **不给因子检验 / 因子归因 / 适配性加跨页"下一步"。** 那是新功能（"指标有效 ⇒ 拿去排序"），
  语义和口径都要重新设计，不在闭环范围内。
- **不抽统一的还原 util。** 六个页面的 form 形状差异大于共性，抽公共层的收益低于成本；漏
  字段的风险用上面第 2 条的测试兜住。

12 个前端测试（含两条各 10+ 字段的还原完整性用例）。方案
`docs/archive/backtest-loopback-plan.md`。

### 9.11 因子归因（#9 / §4.4，2026-09-22 上线）

新页面「因子归因」（`/factor-attribution`）：挑一条**带成交明细**的回测历史做来源，选要
对比的指标，服务端把成交配成往返、比较**盈利单 vs 亏损单**在**买入信号日**的指标取值。
后端 `aquest/factor_attribution/`（trades / values / metrics / service）+
`/api/v1/factor-attribution` 七个端点，历史类型 `factor_attribution`。

**口径（改动前就定死的，别改）**：

1. **方向是事后解释，不是预测。** 与 #5 因子检验正好相反：因子检验问「指标值能不能预测
   未来收益」，归因问「已经发生的这批单，赢的和输的在入场那天取值上差在哪」。所以
   **不产生任何"这个因子可用"的结论**，只给差值与显著性；显著也只是说"赢输两组的取值
   不像随机分出来的"，不是"照着它做能赚钱"。
2. **样本是成交，不是行情面板。** 独立单位是**一笔往返成交**；指标取**买入信号日**的值
   （不是买入成交日——信号日是决策依据，成交日已经混进执行时延）。收益率用
   **净收益率** `pnl / cost_basis`。
3. **证据一律是差值不是比值**（与因子检验、标的检验台同一条铁律）：盈组均值 − 亏组均值；
   再除以合并标准差给出标准化差值，方便跨量纲对读。
4. **未平仓不入胜负。** 只统计已配对的往返；卖不掉的持仓既不算赢也不算输，单独计数并提示
   ——把它算成亏损会让"死扛"看起来像因子失效。
5. **缺值丢弃，不填零。** 指标在信号日取不到值就丢掉这笔成交，丢了多少写进 note。填零等于
   凭空造一批"指标值 = 0"的样本。
6. **置换按块搬动，BH-FDR 对整族只做一次。** 块长按**自然日跨度**换算（不是信号日条数）
   并兜底至少 4 块——按条数算会退化成 2 块，p 值虚高到 0.47 / 0.5，看着像"完全不显著"
   其实是块太粗。
7. **不重跑回测。** 只读来源记录里已存的 `trades`，归因永远能对回那一次回测。

**四道样本护栏**：总成交 < 10 不跑；盈/亏任一组 < `min_group_trades`（默认 20）标「样本
不足」且**不作数**（p 再小也不判显著）；信号日不足 10 个不做置换；整组取值恒定（标准差
为 0）直接标常量、不算差值。

**明确不做**：给因子排名打分、自动挑"最显著的因子"、把归因结论接回条件研究当候选
（一个是解释、一个是发现，混起来就成了用同一批单既挖又验）、支持未平仓持仓的"浮盈"分组。

28 个后端测试（22 单测 + 6 集成）+ 13 个前端测试。方案 `docs/archive/factor-attribution-plan.md`。

### 9.10 候选库 + 显式发布（4.3，2026-09-21 上线）

条件研究挖出的候选条件持久化，带证据快照与采纳状态。后端 `candidate_library` 表 +
`aquest/candidate_library/`（models / evidence / publish / service）+
`/api/v1/candidate-library`（列表 / 入库 / 读取 / 改状态 / 删除 / 发布预览 / 发布）。

**口径（改动前就定死的）**：

1. **永不自动上线。** 发布只写一条 `tracking_status='off'` 的策略，发布路径里没有任何地方
   调用 launch；上线是策略追踪页的显式动作，因为上线日会冻结研究段基线。
2. **采纳与发布是两步。** pending → adopted → published，没有 pending 直达 published 的路；
   **绝不自动把通过置换检验的候选标成已采纳**——统计结论不等于人的表态。
3. **证据是快照，且必须标出处。** 入库时把提升倍数、置换 p 值、支持数、留出期、滚动复验、
   敏感性整份复制（历史只留最近 20 条），同时存来源研究 id 与研究区间以便溯源。
4. **发布不改证据、不给评价。** 只把条件按方向合并进来源研究那套配置（买入 AND 收窄、
   卖出 OR 触发、来源规则为空时替换），不重算绩效、不打分。

**猜不出来的一律拦着报**：缺排序规则、缺离场规则（研究拿「持有到期末」当卖出基准，策略
不行）都会在预览里变成 blocker 让人补，不悄悄填默认值。

**明确不做**：给候选打分排名、自动清理/归档、一次发布合并多条候选、接策略发现的候选
（粒度是整套配置，差一个量级，表留 `source` 字段将来另开）、定时或自动上线。

### 9.9 筛选方案保存 / 加载（4.2，2026-09-21 上线）

公式选股页整套可复现的输入存成命名方案。后端 `screen_presets` 表 +

`/api/v1/screen-presets`（列表 / 读取 / 新建 / 改 / 删）。

**口径（改动前就定死的）**：

2. **加载只还原设置，不自动重跑。** 提示写明「结果需要重新扫描」。

### 9.8 标的检验台（#6，2026-09-21 上线）

新页面「标的检验台」（`/instrument-lab`）。后端 `aquest/instrument_lab/` +
`POST /values`、`GET /conditions/library`、`POST /conditions/check`、`POST /backtest`。
K 线不新造接口，复用 `/market-data/local/{market}/{code}/bars`。

**口径（改动前就定死的）**：

1. **不做综合评分、不排名、不打标签。** 只给可核对的读数：指标值、自身历史分位、命中数、
   收益差、置换 p 值。
2. **分位是「自身历史分位」**，不是全市场分位。单只票没有横截面可比性，界面必须写明口径。
3. **证据是差值不是比值**：命中组前瞻收益均值 − 全样本均值（当日收盘 → N 日后收盘，与因子
   检验同口径）。显著性走连续日期块置换；一次检验多条时 BH-FDR 校正。
4. **该闭嘴时闭嘴**：命中 < 20 标「样本不足」且**不判显著**（p 再小也不作数）；可用交易日
   < 60 不做置换；不显著就写「和随机挑几天没有区别」，绝不写「有效」。

**明确不做**：多标的对比（#16 已有归一化叠绘，重复）、「自动挑出这只票最优的条件」（挑选
偏差）、复活独立的单股回测页（它的价值在买卖点画回 K 线，放检验台里就够）。

### 9.7 回测历史对比（#16，2026-09-21 上线）

新页面「历史对比」（`/history-compare`）：从**跨类型统一存储**的 `backtest_history` 里挑
2~5 条记录，归一化叠绘曲线 + 指标并排 + 各类型专属指标卡。后端 `aquest/history_compare/`
（models / extract / service）+ `GET /api/v1/history-compare/candidates`、
`POST /api/v1/history-compare`；历史面板每条多了「对比」入口（带 `?ids=` 预选）。

**口径（改动前就定死的，别改）**：

1. **不同口径的曲线绝不叠绘**。只有三种口径：资金曲线（`equity`）、多空累计价差
   （`factor_long_short`）、累计 IC（`factor_ic`）。同口径不足 2 条就不叠绘，只画单条并说明。
   因子检验的累计序列**不做归一化**（没有本金概念），画进净值图里会被当成收益曲线。
2. **净值归一化只除以本金**（`performance.start_cash`），取不到才退回除以首值，并且必须
   在图上写明用了哪一种——本金不同的两次实验，收益率口径才是可比的。
3. **跨类型只比规模与显著性，收益类只能定性参照**。统一指标表的每一格都带 `source`；
   拿不出来的格子显示「—」+ 原因，绝不用 0 填。不做综合评分、不给排名。
4. **可比性警告由服务端生成**：曲线口径混杂、区间不重叠、类型混合、样本长度差 ≥3 倍
   （长样本天然更容易撞上极端回撤）都要直说。
5. **曲线点数上限 1200**，超出等距抽样但**首尾必留**（末值是最该看的数字）。

**诚实结论（页面上就写着）**：只有组合/单股回测有真正的资金曲线；条件研究、波段研究、
策略适配性都不产生曲线，它们只能比样本规模、显著性与各自的专属指标。

20 个后端测试（含 5 个集成）+ 11 个前端测试。方案见 `docs/archive/history-compare-plan.md`。

### 9.6 单指标 / 因子检验页（#5，2026-09-21 上线）

把"这个指标本身能不能给股票排序"做成正门。新增 `aquest/factor_test/`（`panel` 预算 +
两遍建面板 / `metrics` 打分 / `service` 编排）、`/api/v1/factor-test` 四个端点、历史类型
`factor_test`，前端 `FactorTestPage`（指标多选 + 前瞻天数 + 分档数；结果 = 总表 + 每日 IC 曲线 /
IC 累计 / 多空累计三张手写 SVG + 分层柱状）。

**口径（改动前就定死的）**：

1. **标签是前瞻收益，不是事件。** 所以不沿用波段研究的"命中率之比"——两个负数相除会读成
   "差三倍"，实则是"亏得少"。证据一律是**差值**：分层收益、多空价差。
2. **独立单位是交易日，不是单元格。** 5000 只 × 1000 天看着是 500 万个观测，
   但股票共用同一个市场时钟；秩相关在每日横截面内做，置换按连续日期块整块搬动。
3. **置换走 Gram 矩阵**：`gram[t,u]` = 第 t 天的值 vs 第 u 天的收益的相关。
   实测在它的对角线上，一次日历置换只是换一批格子 —— 200 次置换不必重算 20 万次相关。
4. **多空曲线累加不复利**，t 值按 `N/h` 折算独立样本（重叠窗口不折算就是骗自己）。
5. **不做样本外切分**：方向（买高/买低）是看全样本符号定的，前后半段一致只说明
   "不是某一段独撑"。页面上照此写，不写用户一定会误读。

**三条护栏（真机跑通后补的，详见 `docs/archive/factor-test-plan.md` §3.7）**：p 值过了但 IC 只有
噪声门槛的 1.0 倍不许说"强度可观"（`CLEAR_IC_RATIO = 2.0`）；分层倒挂容差取**阶梯跨度的 5%**
（`LAYER_INVERSION_TOLERANCE`，否则前三档只差万分之一也会被报"3 处倒挂"）；多空胜率 < 55%
要直说"接近抛硬币，扣掉成本未必可执行"。**半段的符号必须内部留着** —— 对外存绝对值，
但"方向相反"是符号的命题，从绝对值上读永远触发不了。p 值有下界 1/(N+1)，alpha 设得比它还低
时 `reason` 直说原因，不让"全部不显著"被读成"这些指标都是垃圾"。

### 9.5 参数敏感性分析（#3，2026-09-21 上线）

每个挖掘候选带一条 **5 点阈值邻域曲线**（`sensitivity` 字段）：把切点往松、往紧各挪两档
（分位 ±5% / ±10%）重新计分，输出每档的阈值、命中数、胜率、lift，以及核心读数**保持率**
`(lift−1)/(基点 lift−1)`——1.00 一点没掉、0.50 掉一半、负数表示优势打反。

**口径（改动前就定死的，别改）**：

1. **扰动在分位空间，不在阈值的算术空间**。阈值 ±10% 对不同量纲的指标含义完全不同
   （一个阈值 10.2、另一个 0.03），而且一半的条件是「A > B」、根本没有常数。统一归约成
   「差值序列 + 阈值」（`X≤c` 取负成 `−X ≥ −c`，`A>B` 用 `A−B` 且基点 0），再按分位挪。
2. **度量用挖掘自己的口径**：命中样本按交易组去重取首次、胜率取均值、基线取分组等权，
   一步都不改。**基点用原始阈值直接算**（不按分位重建），所以候选表和邻域表基点是同一个数。
3. **保持率的分母没有意义时给 null**：`基点 lift − 1 ≤ 1e-12` 就不算有优势（与衰减比同一门槛）。
4. **命中样本 < `min_trades`、或阈值退化到恒真**的档位标 `insufficient` / `degenerate`，
   从 `stable_offsets` / `evaluated_offsets` / 中位 / 最差里一起剔除，不记成"没通过"。
5. **不给稳健度评分**，只给事实数字——与衰减比、滚动一致性同一立场。

**边界必须说清**：邻域是在**挖掘样本（寻优期）**上算的，回答的是「这个切点是不是噪声尖峰」，
**不代表样本外表现**；样本外由验证期、留出期、滚动复验负责。真要做样本外邻域，得把验证期
样本也建出来（每只股票多跑一轮回测并回传特征矩阵），接口不用动，只换入参。

### 9.4 挖掘结果相关性去重（#4，2026-09-21 上线）

候选按命中向量的 **φ 系数**合并同义条件，门槛 `duplicate_correlation`（默认 0.6，可配 0.5~1.0）。
被合并的条件**不删除**，挂在保留那条候选的 `duplicates` 里（条件文本 + ρ + lift + 样本数），
界面在条件名后显示「已合并 N 条」，悬浮看明细。

**口径（改动前就定死的，别改）**：

1. **φ 只在两条条件都可评估的样本交集上算**。各指标有自己的缺口，不在交集上算等于
   给一条条件白送它根本没机会命中的样本。
2. **取 ρ ≥ 门槛，不取 |ρ| ≥ 门槛**。ρ ≈ −1 是互补条件（一条的反面），是相反的发现。
   而且它们不可能同时优于基线（两者把样本切开，加权平均就是基线），所以取符号不影响结果。
3. **默认 0.6**：同一指标相邻分位阈值 ρ = √(p(1−q)/q(1−p)) ≈ 0.61~0.67 → 合并；
   相隔一个分位 ≈ 0.41 → 保留（那是不同的激进度）。调到 1.0 ≈ 关闭，
   **但 0.995 Jaccard 的兜底仍在**，所以"关闭"不等于完全不去重，文档要写清。
4. **列联表退化时（分母为 0）返回 None，不猜值**；此时退回落回 0.995 的重叠规则。
5. **合并不减少候选条数**：空出的名额由排序更靠后的不同义条件顶上。

### 9.3 滚动样本外验证（#2 的方案 A，2026-09-21 上线）

条件研究新增「滚动复验窗口数」（1~5，默认 1）。>1 时把最终留出期切成 K 个首尾相接的连续窗口，用同一批候选在每个窗口各回放一次，基线同窗重算，于是每个候选拿到 K 份互相独立的样本外成绩。

**口径（改动前就定死的，别改）**：

1. **挖掘只在训练段做一次**，各窗共用同一批候选。这才谈得上"同一个条件在几个窗口里的表现"。真 walk-forward（每窗重挖）要能判定跨窗条件是否同义之后才有意义，那依赖 #4 相关性去重。
2. **窗口内成交数 < `min_trades` ⇒ 标「样本不足」，从 `evaluated` 分子分母一起剔除**。没样本不等于没通过——否则一个短窗口会被读成"这条条件在这个窗口失效了"。
3. **每窗至少 30 个自然日**，放不下就自动减少窗口数并写进 `rolling.note`；降到 1 窗时不跑滚动复验（跟不开是同一件事，没必要多跑一轮逐股回放）。
4. **不给"稳健度评分"**，只给「N 窗里 M 窗优于基线」+ 中位/最差胜率 + 每窗原始数值。阈值该由用户的用途决定——与策略追踪的衰减比同一立场。

存储与兼容：`holdout`（整段留出的合成值）保持不变，新字段 `windows` / `consistency` 是增量，老的历史记录照样能读。成本约为现状 +20%（留出段只占 20%，K 个窗口加起来等于再跑一遍留出段）。

### 9.1 基准对照（原 #15，2026-09-21 上线）

### 9.17 股票组：把选出来的票留下来观察（#26，2026-09-22 上线）

起因是用户的一句话：「那其实也应该有个按钮一键应用到公式选股里面去进行选股。并且，
公式选股应该可以一键把选出来的股……保存成一组。然后最好还能观察选入组后整体的涨跌幅
表现。」——**选完之后没有下文**，是这个页面最大的洞：扫出几十只票，导出 CSV，然后这批票
就再也没有人回来对过账。

三件事一起交付，因为它们是一件：

| | 做了什么 | 现状 |
|---|---|---|
| **A** | 条件研究 → 公式选股一键桥接 | 规则结构同构（`signals / conditions / combine_mode / minimum_matches`），只差 `required_conditions` 在选股侧无对应项 |
| **B** | 结果勾选 / 整批保存成组 | 完全没有：结果表既无 checkbox 也无保存按钮；新建 `stock_groups` 表 |
| **C** | 组内表现的观察曲线 | 白捡：`portfolio_backtest/benchmark.py` 的等权买入持有 + `universe="codes"` 早已具备 |

**口径（三条硬规则，与组合回测基准共用同一份实现）**

1. **等权买入持有**：起点按收盘价每只各买等额金额，之后不动。不是每日再平衡——再平衡
   是另一种策略，不该混进观察里。
2. **起点必须有价**：起点当天没有收盘价的标的直接出局（新股、停牌）。用后面才有的价格
   回填等于默认「停牌之前也买得到」，把幸存者偏差塞进结论。出局的标的在结果里**单独点名**，
   因为「这一组到底算了几只」是判断可信度的一部分。
3. **超额用差值不用比值**：两条曲线都可能为负，负 5% 与负 10% 相除会读出「差两倍」这种
   符号都未必对得住的结论；相减才是「多赚/少亏了 5 个百分点」。

全市场对照走的是同一个函数、同一套规则（把 benchmark 的绩效计算提成公共的
`curve_performance`）。这不是洁癖：各算一套的话同一批票在两页上会给出不同的最大回撤，
而没人会去查这种差异。

**A 的语义差异必须讲出来**：条件研究评的是「什么时候进、什么时候出」，选股只回答
「某一天是否满足」。所以只搬买入侧，卖出规则不带——带了也是摆着不用，反而让人以为它被
算进去了。`required_conditions` 在选股侧没有对应概念，处理办法是并入普通条件并在提示里
说明：在「全部满足」下两者等价，在「任一满足 / 至少 N 条」下语义变了（原本无条件生效的
变成参与计数），必须让用户核对。

**不做的事**：组不交易——不产生买卖信号、不模拟调仓、不假设买了多少。想看带调仓的结果
是组合回测的职责。

**实测**：5000 只 × 1200 天（600 万行）读 0.93s + 透视 2.27s；一年窗口 0.65s。按这个量级
走同步接口，不值得为此引入一轮任务轮询。

**2026-09-23 补：折叠态 / 展开态两档（用户提出"存很多组时打开这页会不会很卡"）**

先把误区说清：打开页面本来就只拉一次轻量列表，计算只发生在点某个组时——所以「打开就卡」
在旧版也不成立。真正会卡的是**把所有组扫一遍**：`performance` 每组起点不同，组与组之间
没法复用同一份行情，20 个组就是 20 次全市场扫描。所以按"信息分档"重做：

| | 显示什么 | 代价 |
|---|---|---|
| 折叠态（默认） | 组名 / 只数 / 入组日期 / 来源 / **筛选条件快照** / 近 1 月、近 3 月收益与超额 | 列表零计算；阶段收益走 `GET /stock-groups/summary`，**所有组共用同一窗口同一份行情，一次请求算完**（近 60 日约 40 万行，对比全量 600 万行） |
| 展开态 | 入组至今曲线、组内分布、成员表 | 点开才算一次，结果按组缓存，切走再回来不重算 |

两条刻意的决定：

1. **两组数字不同源，必须在 UI 上写明。** 折叠行是「近 N 个交易日」（同窗口、组之间可比），
   展开是「入组至今」（每组起点不同、不可比）。不写明的话 100% 会被当成同一个东西对比。
   窗口按交易日数而非自然日（假期不算），凑不满时标出实际天数，不把 41 天当 60 天看。
2. **组数不设上限**，列表默认只铺最近 20 条、剩下显式点开。用户最初提的是「只允许存 10 组」，
   没采纳：组的价值锚在**入组日**上，删掉就再也补不回来（行情可以重下，但"我哪天决定关注
   它"这个事实没了），硬上限会逼人删历史。

**筛选条件存快照，不回指历史**（新表 `stock_group_criteria`）：扫描历史每种类型只留最近
20 条，等组还在、历史已被淘汰时，只有组里的快照还能回答「这批票是按什么选出来的」。放新表
而不是给 `stock_groups` 加列，是因为加列要 bump `SCHEMA_VERSION`（老库先整库备份 4.6GB），
而这里要迁移的旧数据是「空」。表已进 `ASSET_TABLES`，随用户资产导出。

顺带补上**改名**：后端早有 `PATCH` 接口，页面上此前没有任何入口——名字存了就改不了。

**存储取舍**：新表 `stock_groups` 用 `CREATE TABLE IF NOT EXISTS` 加，**不 bump
SCHEMA_VERSION**——bump 会让每个老库先整库备份一份（4.6GB），而新表不需要迁移任何旧数据。
成员整份存 JSON 而不是拆子表：量级是几十只、读写都是整取整存，拆表只会多一次 join 且
没法保住用户的勾选顺序。已加进 `ASSET_TABLES`，否则导出导入会漏掉它。

15 个后端测试（9 单测钉住口径 + 6 集成）+ 3 个前端测试。

### 9.18 策略追踪：下一交易日计划 + 成交明细分段（#1 续，2026-09-23 上线）

起因是用户一句「可以看看 同类产品 是怎么做的，**分成成立前后，还有明天的交易提示，告诉
用户明天会调仓成什么标的，交易明细也分成成立前后**」。

先核对了 同类产品 的做法：`launch_date` 作分界、净值曲线画红虚线、分别给
`backtest_return_rate` / `live_return_rate`、交易指南只有**文本**、成交明细在同一个 tbody
里加 sectionHeader 分三组（上线后 / 上线前 / 其他）。**我们分段展示本来就有**（研究段与
观察段两张卡片并排，还有衰减比和 MinTRL），所以真正缺的是后两件：

| | 做了什么 | 关键判断 |
|---|---|---|
| **A** | 下一交易日计划（明天卖什么、买什么） | **不另算一套预测** |
| **B** | 成交明细按上线日切两段 | 上线后默认展开、上线前折叠，每段上限 200 条 |

**A 的全部依据是一条事实**：主循环的撮合 lag 恒为 1 根 K——T 日收盘判定、T+1 开盘成交。
所以「明天的单」就是模拟收尾时**还挂在 `pending_sells` / `pending_buys` 里、本来会被直接
丢掉**的那批。不需要新增一次模拟：调度器每天本来就在全量重跑全天，边际成本为零。卖出侧
回款用今日收盘价估，买入侧用 `available = cash + 估算回款` 再走既有的 `_planned_shares` /
`_affordable_shares`，与真实下单走的是同一段代码。

两条口径必须硬守：

1. **估算的就是估算的。** 明日开盘价未知，买入只能给 `estimated_size` / `estimated_cost`，
   字段一律带 `estimated_` 前缀（防下游当实际值用），界面明写「估算值，实际以明日开盘价
   成交」。卖出侧是持仓**实际**股数，今天就已经定了——这一栏不带前缀，不能含混。
2. **月 / 周频策略要掐掉假计划。** 主循环里最后一根 bar 恒被判为调仓日
   （`index == len(dates)-1`），所以非 daily 频率的策略每天收尾都会攒出一批候选。新增
   `_rebalance_due` 按次日是否跨周 / 跨月判断：**不是调仓日就不给买入计划**，并在 notes 里
   说明原因。不给数比给一个「明天按周频调仓」的假提示诚实。

**B 的分段判据必须与净值曲线一致**：`成交日 >= 上线日` 算上线后。两边各算一套的话，同一笔
成交会出现在「看起来属于研究段」的位置上，而没人会去查这种错位。明细**全量覆盖而非增量
合并**——它与净值出自同一次模拟，增量合并会在策略改规则后留下孤儿行。列表接口（
`GET /tracking`）把 `trades` 置为 `null`：明细大而列表页不用，展开时才单独取。

**存储**：新增 `strategy_tracking_trades`（主键 `(strategy_id, seq)`，`phase` 落库时就算好，
读的时候不再判）与 `strategy_tracking_plan`（每策略一行，upsert 只留最新）。都用
`CREATE TABLE IF NOT EXISTS`，**不 bump `SCHEMA_VERSION`**（bump 会让老库先整库备份 4.6GB，
而这里没有旧数据要迁移）。两张表都已进 `ASSET_TABLES`，否则导出导入会漏。删策略连带删三张
表；**下线只清计划、保留观察段与明细**（那是一段已经发生的事实）。

**不做的事**：不预测明日开盘价、不预测明日是否触发止损、不建模停牌与一字板（引擎本身也没
建模，单独在这里做一半的因果是新的偏差）。计划里的数字只是「按现在的规则，明天大概率会
发生什么」，不是委托单。

**测试**：9 个后端测试（2 个钉住 pending 单的导出与月频门控、5 个钉住落库与连带删除、
1 个集成钉住列表不带 trades / 详情带分段）+ 3 个前端测试；`pageGuides.json` 补两条步骤与
两条限制并重新生成手册。

### 9.19 研究方案：买卖条件研究页整套输入可存成命名方案（4.2 补，2026-09-23 上线）

公式选股页早就有「筛选方案」（§9.9），但买卖条件研究页只能靠**历史记录**回看——而历史是
**满了自动淘汰**的（上限 20 条，跑得多就被挤掉）。用户要的是「还想再跑一遍」的东西，那个
不该被挤掉。**方案与历史是两件事**：历史记"跑过什么"，方案记"还想再跑一遍"（只有显式删才
消失）。所以这次把同一套能力补到条件研究页，叫**研究方案**。

存的东西就是**跑研究时发的那个请求本身**——历史记录里的 `request` 也是它，两者同源。

**校验策略与筛选方案相反，这是有意的。** 筛选方案是**白名单裁剪**（把不支持的字段悄悄丢掉，
再往 notes 里写一句）；研究方案是**复用 `ConditionResearchRequest`、非法一律 422**。原因是
字段耦合程度不同：筛选条件彼此独立，裁剪一个不影响别的；而研究配置里
`position_mode` / `fixed_size`、排序指标与公式输出这些字段互相咬合，**悄悄改一个会把整套
规则的语义改掉**。宁可拒绝，不要静默改。

**存储**：新表 `research_presets`。

- 用 `CREATE TABLE IF NOT EXISTS`，**不 bump `SCHEMA_VERSION`**（bump 会触发 4.6GB 整库备份，
  而这里没有旧数据要迁移）。
- **分开建表，而不是给 `screen_presets` 加一个 `kind` 列**：DuckDB 的
  `ALTER TABLE ADD COLUMN` 不支持 NOT NULL / DEFAULT，加列＝裸列 + UPDATE 回填，比新表麻烦。
- 已进 `ASSET_TABLES`，否则导出导入会漏。
- 上限 60 个、名字唯一（改名时排除自己）、覆盖保存不抹 `created_at`。

**前端**：面板沿用公式选股页的骨架（下拉选方案 + 保存 / 另存 / 覆盖 / 加载 / 改名 / 删除 /
**一键研究**）。两个细节：①「加载」只还原输入不重跑，「一键研究」＝加载 + 立刻跑；②加载时
统计**失效引用**（方案里引用的指标 / 公式现在不存在了）并据实提示——与筛选方案那套
`missingReferences` 一致，不静默丢字段。

**测试**：19 个后端测试（10 单测钉住往返 / 重名 / 上限 / 覆盖不抹创建时间，9 集成钉住五个
端点与非法 payload 422）+ 5 个工具函数测试 + 3 个页面测试。

### 9.20 使用手册单页（目录 + 搜索）（#25 续，2026-09-23 上线）

用户一句「手册在页面上怎么没有做个单独的页面，我希望还支持目录和搜索功能」。此前手册只有
两个出口：每个页面顶部那个折叠块，以及仓库里生成的 `docs/user-manual.md`。前者要一页一页
翻，后者不在产品里。

**新开 `/user-manual`**：左侧目录 + 搜索框，右侧是 13 个页面 + 手册页自己的全部说明。

**内容仍然只有一份**（`pageGuides.json`）——这一页、页内折叠块、Markdown 手册三处都由它
生成。这是 §9.13 定下的规矩，手册页没有另起一套文案，只是同一份数据的一个新视图。手册页
自己也有一条说明条目（`user-manual`），因为守卫测试要求「每个页面都挂了一份说明」；为此
把它的措辞写成对两个出口都成立（不出现「这一页」这种只在网页版成立的说法）。

**搜索的取舍**：字面包含匹配，按空白分词，多词之间是「都要出现」。**不做分词、不做同义词**
——中文分词要引一整个词典，而这里的语料只有十几页，收益不抵复杂度。代价写在页内说明里：
只写了「佣金」的地方，搜「手续费」搜不到。不假装懂同义词。

两条行为规则：

1. **标题或摘要命中 ⇒ 整节保留**；只有要点命中 ⇒ 只留命中的那几条。用户搜「因子归因」时
   要的是那一页，不是那四个字；搜「手续费」时要的是那一条。同一套过滤给不出两种结果，
   所以按命中位置分了两类。目录项上显示该页命中了几条。
2. **高亮用 `<mark>` 而不是 `v-html`**。内容是静态 JSON，但 `v-html` 是把注入口子提前挖好，
   不值得为省几行代码冒这个险。切段在 `utils/manual.ts` 里做（多词命中区间要合并重叠部分）。

**锚点跳转**用原生 `#id` + CSS `scroll-margin-top` 让开 sticky 顶栏，不写滚动脚本。守卫测试
里加了一条「目录 href 与正文 id 一一对应」——这两者一旦漂移，现象是点了目录没反应，谁都
不会想到去查 id。

**测试**：15 个（8 个工具函数 + 7 个页面）+ 既有 `pageGuides` 守卫 8 条自动覆盖新页面
（说明条目、路由分支、13 个页面的导航链接补齐）。

### 9.21 策略追踪详情：账户快照、当日候选与完整成交分页（#1 续，2026-10-01）

下一交易日待执行计划分开。曲线继续只覆盖上线后的观察段，研究段保留为历史绩效参考。

### 9.22 成交口径统一：风控退出改次日开盘 + 持仓风控线可视化（2026-10-15）

**这一条改的是研究口径本身，不是实现细节。** 引擎的撮合 lag 恒为一根 K（T 日收盘判定、T+1 开盘
成交），但风控退出过去是在**触发当根 K 线内按触发价平仓**——那个价格只在盘中存在，而系统每天只在
收盘后批处理：既不可能提前知道它会出现，也来不及挂单。于是模拟给出的成交是用户实际拿不到的成交。
顺带查出三处同源的不一致，一并在这次修正里处理。

**四处口径同时变**（都会移动 3000 组退出风控寻优的目标函数，挑出的参数与整市场榜单必然重排）：

1. **成交日**：`_execute_risk_sells` → `_queue_risk_exits`，判定输入完全不动（仍用 T 日 OHLC 与 T 日
   ATR、止损→移动止盈→止盈的优先级、`highest_price` 先折叠再判），命中就登记成挂单，与规则卖出共用
   同一根 K 线滞后；`execution="next_close"` 时落 T+1 收盘。冷却锚点从触发日改到**成交日**
   （`cooldown = 成交日 index + cooldown_days + 1`，与原实现等价地平移一根）。
   **Python 状态机与 numba 内核必须同提交改**：寻优跑内核、报数字走状态机，半迁移等于优化一个口径、
   展示另一个口径。内核复用现成的 `ps_slot/ps_sig/ps_reason/ps_cd` 队列，`ps_reason` 的 id 2/3/4 就是
   触发身份，因此不新增 `ps_risk`；恢复检查点时校验 `reason` 与 `risk_trigger` 自洽，对不上就交回原实现。
2. **最长持有天数进组合模拟**：`_pool_portfolio_config` 原先不设也不覆盖 `max_hold_days`，每条策略自己
   定义的 20 个交易日只在逐股回放里生效，组合持仓可以无限拖着不卖。现在 `_SYMBOL_RISK_FIELDS` 含该项，
   到期按**每标的生效后的**配置强制登记卖出；全局仍保持 `None`，不给没定义的标的凭空加限制。
3. **ATR 周期真的可按标的覆盖**：原先被两处校验器钉死在 14，另有四处硬编码字面量把传入值丢掉——覆盖
   通道列了字段却不通，属于「看起来支持」。撤掉校验、改为透传，并修掉底座构建顺序（`context.py` 曾在读
   `symbol_strategies` 之前就用全局周期建好底座）。**寻优仍不搜周期**：这一条只让参数生效，不扩搜索空间。
4. **ATR 平滑统一到 Wilder**：风控线原来是简单移动平均，而指标目录给用户看的 `atr_pct` 是 Wilder，
   同一个名字两套算法，界面与引擎的线永远对不上。两个引擎共用同一个 `_atr_series`，一处改完两边同时变。

**显示出来的必须是引擎实际在用的那几条线**：持仓行新增三档价（`stop_loss_price` /
`trailing_stop_price` / `take_profit_price`）、`risk_level_as_of`（判定用的那一日）、`highest_price`、
挂单出处（`pending_exit_reason/signal_date/risk_trigger`）与持有到期（`max_hold_days` /
`max_hold_days_left` / `max_hold_expiry_date`）。它们与判定共用 `_risk_config_for_symbol` 的同一份覆盖
结果，否则显示会与实际脱钩。未启用的规则给 `None`，界面留空、**不许显示 0**；到期日只有行情覆盖到那
一天才给得出。这些字段只存在于回放尾部的 `current_state`，**不塞进 `_state_record`**——`states` 会序列化
进每个检查点 blob，等于给每只标的乘上几千行展示数据；由 `account_summary(current_state=...)` 按标的并回
展示行。渲染四处：全市场页当前持仓面板、策略池详情跟踪持仓、下一交易日计划的「触发来源」列、全市场与
特别关注表格的状态列。

**版本盐**：`pool-account-v2 → v3`（跟踪账户在新口径下重建）、`market-pool-v6 → v7`（进
`config_fingerprint`，否则「增量更新策略池」会把新旧口径混在同一池里复用）。检查点格式**不升 version**：
研究侧多段检查点是进程内的，池跟踪另有更硬的盐；反序列化对新键取默认值，旧形状 blob 仍可读。

**不做的事**：不建模涨跌停 / 停牌不可成交（保留免责句，方向上仍偏乐观）；不做新旧口径并存的开关或兼容
层；不迁移旧策略池条目——用户改完代码后清空并重建全市场（约 17 天，需等改动上线后再起跑）。

**验证**：`test_fast_portfolio_sim.py` 三路对拍（原实现 / JIT / 纯 Python 内核）继续逐字段相等，并新增
「风控单恰好挂起在检查点边界」的用例——那是 `init_ps_cd` 与恢复守卫的唯一载荷；`run_sim` 的
`portfolio:hit == 1` 断言防内核静默回退（曾因 `**kwargs` 触发 `UnsupportedBytecodeError` 静默失效）。
风控口径测试按新日期重写，不保留旧断言。

### 10.5 strategy_pool 多副本调度与写入串行性

三处都没有跨进程保护：

- `strategy_pool/tracking_scheduler.py:33-94`：进程内 `_WRITE_LOCK` + SELECT→INSERT 之间**无 DB 唯一约束**，
  且它是唯一没挂在 `owns_runner` 门禁下的 scheduler（`web/app.py:302-312`）；
- `store.py:214-219`：reset 与其它写入没整体串行，晚到的 upsert 会把刚删空的条目写回并留下孤儿版本；
- `tracking_store.py:238-263`：`save_snapshot` 的校验与 UPDATE 是两条独立 SQL，**无事务包裹**。

**附带观察**：`indicators/cache.py:814-832` 内存层有 `full_history` 保护，但 `:1088-1131`
`_persistent_put_many` 没有——任何以窗口 frame 调用 `get_or_compute`（默认 `persist=True`）都会
落脏条目。现有两个调用方（`portfolio_backtest/context.py:499` 显式 `persist=False`、
`backtest/service.py:319` 传全序列）恰好规避，**属尚未被触发的缺口**。
