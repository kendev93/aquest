# 滚动样本外验证（backlog #2）实施方案

> 状态：**已按方案 A 实现并上线（2026-09-21）**。方案 B（每窗重挖）待 #4 相关性去重之后再做。
> 实现与文档的三处细微差异以代码为准：窗口长度字段叫 `calendar_days`（按自然日，与现有切分口径一致，不是交易日）；结果里 `rolling.note` 也承载"窗口数被降级"的说明（候选的 `consistency.note` 只说样本不足）；**降级到 1 窗时视为未启用**，不再多跑一轮逐股回放。

## 1. 为什么做

条件研究现在是 **60/20/20 单次切分**：训练段挖候选、验证段过约束、留出段复验一次。**结论依赖这一次怎么切**——同一批数据换个切法，挖出来的条件和它的表现可能完全不同，而我们没有任何东西去验证这个稳健性。

我们已有的防过拟合手段：置换检验（200 次，标定过误报率 5%）、BH-FDR（波段研究）、因果无前视适配、时间切分留出。**缺的正是"切分本身"这一环。**

立场不变：只做能被证伪的东西。所以输出是「K 个窗口里 M 个优于基线」这种可核对的数字，**不做"稳健度评分"、不给通过/不通过的硬阈值**（与策略追踪的衰减比同一立场）。

## 2. 现状盘点

`condition_research/service.py::ConditionResearchService.run` 的主流程：

1. `time_split.split_calendar_range(start, end, train_ratio=0.6, validation_ratio=0.2)` → `train` / `validation` / `holdout`
2. **训练段**：逐股回测（5344 只 × 训练段）→ 盈亏样本 → `mining.py` 挖候选（对比式阈值 + 两两规则），带置换门槛
3. **验证段**：所有候选 + 基线回放 → 约束（`min_trades` / `min_instruments` / 显著性）→ 排序选 top N
4. **留出段**：`holdout_candidates`（每侧 1~3）个候选 + 基线回放 → `full_period` + `holdout`

成本结构：**第 2 步（逐股回测）是绝对大头**，第 3 步次之，第 4 步最小。

复用的两个现成件：

- `time_split.split_calendar_range` —— 按比例切成三段，返回 `ResearchSplits`
- `_candidate_window_task` + `CandidateWindowPayload` —— **在任意日期区间上回放任意候选集 + 基线**，正是多窗口复验需要的那一层

## 3. 两种做法

### 方案 A：同一批候选，多窗口复验（rolling validation）

挖掘只在训练段做一次；把**留出段切成 K 个连续窗口**，逐个回放同一批候选 + 基线。

- 回答的问题：**这条挖出来的条件，换个时间段还成立吗**
- 成本：≈ 现状 + K×留出段回放（留出段只占 20%，K=4 时总增幅约 15~25%）
- 一致性定义清晰：同一个条件在 K 个独立窗口里优于基线的次数

### 方案 B：每个窗口独立重挖（真 walk-forward）

K 个滑动的训练窗各自重跑全流程（含挖掘 + 置换检验）。

- 回答的问题：**这套挖掘流程本身，在不同时间段能稳定产出好东西吗**
- 成本：≈ K × 全流程（5 窗 ≈ 5 倍时间，粗估 20~40 分钟）
- 硬依赖：跨窗口要说"同一个条件"，得先能判定两个条件是不是同义（阈值差一点算同一个吗）⇒ **这正好是 backlog #4「挖掘结果相关性去重」要做的事**

## 4. 推荐：先 A，B 排在 #4 之后

- 成本差一个数量级（A ≈ +20%，B ≈ +400%）
- B 的"一致性"判定依赖条件相似度，先做 #4 再做 B 更顺
- A 已经能回答用户最关心的那个问题：我挖出来的这条，未来还灵吗

命名上也别称 A 为 walk-forward——**A 不重挖**，叫「滚动复验」更诚实。

## 5. 方案 A 的落地设计

### 5.1 配置

`ConditionResearchConfig.walk_forward_windows: int = 1`

- `1` = 现状（单窗口留出）；`2~5` = 窗口数
- 窗口放不下时**不报错**，自动把 K 降到能放下的最大值，并在结果里写明（`requested` vs `used`）

### 5.2 切分

新增 `time_split.split_windows(start_date, end_date, count)`：按自然日均分成 K 段，首尾相接、不重叠、不漏（与现有 `split_calendar_range` 的自然日口径保持一致）。每窗最少 30 个自然日，不足则降 K。

### 5.3 执行

复用 `CandidateWindowPayload` + `_candidate_window_task`，每窗跑一次，候选集 = 现有的 `holdout_ids`（每侧 top N），基线同窗重算。

进度：原先 3 段（训练/验证/留出）变成 训练/验证 + K 个窗口，文案带窗口序号（"复验第 2/4 个窗口"）。

### 5.4 输出（新增字段，老字段一律保留）

每个候选新增：

```jsonc
"windows": [
  {"index": 1, "start_date": "...", "end_date": "...", "bars": 60,
   "trades": 812, "win_rate": 0.54, "baseline_win_rate": 0.51,
   "improved_stock_ratio": 0.62, "improved_win_rate": true,
   "insufficient_sample": false}
],
"consistency": {
  "requested": 4, "used": 4,
  "evaluated": 4,             // 剔除样本不足的窗口后的分母
  "better_than_baseline": 3,  // improved_win_rate 为 true 的窗口数
  "median_win_rate": 0.53, "worst_win_rate": 0.47,
  "median_improved_stock_ratio": 0.60,
  "note": null                // K 被降级 / 窗口样本不足时写原因
}
```

基线同步给 `baseline.windows`（每窗的胜率与成交数），否则没法对照。

### 5.5 判定口径

- 只展示：K 窗里 M 窗优于基线 + 每窗数值 + 中位数 / 最差值
- **窗内成交数 < `min_trades` ⇒ 该窗标「样本不足」，从 `evaluated` 分母剔除**（不能把"没样本"算成"没通过"）
- 不做综合评分、不硬判通过与否

### 5.6 与现有字段的关系

`holdout`（整段留出的合成值）**保留不动**，另加 `windows` 明细。理由：`backtest_history` 里已有老结果，改字段语义会让旧记录读不出来。

## 6. 前端

- 「搜索目标与验证」区加「滚动复验窗口数」下拉（1~5，默认 1 = 关闭），helper 写明成本
- 候选卡加一行：`3/4 窗优于基线 · 中位胜率 53% · 最差 47%`；样本不足时显示「—」+ 悬浮说明
- 展开后是窗口明细表：窗口 / 起止 / 成交 / 胜率 / 基线胜率 / 是否优于基线
- `utils/terms.ts` 加 `rollingWindows`、`consistency` 两个词条

## 7. 测试清单

- `split_windows`：均分、不重叠不漏、K 自动降级、K=1 等价原样、区间过短报错
- 一致性聚合：样本不足窗口被剔除、全通过 / 部分通过、中位数与最差、K 降级时 `note` 有值
- service 层：窗口数 = K、基线每窗都算、**K=1 时结果与改动前一致**（回归）
- 前端：窗口数下拉、一致性文案、样本不足显示「—」
