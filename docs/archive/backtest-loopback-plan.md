# 回测闭环（backlog #11）交付方案

> 原话：「结果 → 保存候选 → 一键载入复测。我们有回填，可以做得更顺。」

## 一、它到底是什么

不是新功能，是**把已经跑过的东西拉回表单**。

研究类页面的历史面板现在有「加载」按钮，但多数页面加载后只把**结果**塞回页面、不还原**输入**。
想微调一点再跑一遍，只能凭记忆重填一遍长长的表单——顺带还会漏掉手填时不显眼的设置
（比如排序方向、组合持仓数上限、止损冷却天数）。

闭环 = 一条历史记录 + 一次点击 = 表单回到当时那个样子，改一下就能重跑。

## 二、现状（2026-09-22 调研）

| 页面 | 载入历史后的行为 | 判断 |
| :--- | :--- | :--- |
| ConditionResearchPage | 完整还原表单（`applyStoredRequest`） | **已通** |
| SwingResearchPage | 还原表单（`applyStoredForm`） | 已通 |
| FactorTestPage | 只还原 horizon / value_ids / min_cross_section / permutations | 缺 7 个字段 |
| FactorAttributionPage | 只还原 source / value_ids / min_group_trades / permutations | 缺 3 个字段 |
| StrategyFitnessPage | **完全不还原**，只塞结果 | 缺全部 |
| PortfolioBacktestPage | **完全不还原**，只塞结果 | 缺全部 |
| CandidateLibraryPage | 无回测入口 | 缺最后一环 |

另有：`candidate_library/service.py::import_candidates` 只接受 `condition_research` 类型；
`BacktestHistoryPanel` 只有「加载 / 对比 / 删除」三个动作。

## 三、本次做 / 不做

**做：**

1. 四个页面的历史「加载」真正还原输入（上表缺什么补什么）。
2. 候选库加「载入复测」按钮：用候选的 `source_history_id` 取回来源研究的完整 request，
   桥接回条件研究页还原表单。
3. 载入后的提示统一改成「配置已还原，需要重新运行」——见口径 1。

**不做（明确划界）：**

- **不让非条件研究类型进候选库。** `import_candidates` 只认 `condition_research` 不是缺陷：
  候选库的条目带一份证据快照（§9.10），item 的 lift / 置换 p 值来自条件研究的挖掘口径。
  波段研究、因子检验、适配性评估的产物**没有这些量**，硬塞进去要么留空（造出一条没有证据的
  条目），要么套用不相干的指标（不可证伪）。保持「候选 = 可验证的买卖条件」才是它的价值。
- **不加「历史 → 重跑」的后端端点。** 历史记录里本就存了完整 request，还原是纯前端的事，
  加服务端接口只会多一条要维护的路径。
- **不给因子检验 / 因子归因 / 适配性加跨页「下一步」。** 那是新功能（"这个因子有效，所以拿去
  排序"），语义和口径都得重新设计，不在闭环范围内。
- **不做统一的还原 util。** 六个页面的 form 形状差异大，抽公共层收益低于成本；见口径 3 用测试
  收口。

## 四、口径（改动前就定死的）

1. **加载 ≠ 重跑。** 历史记录存的是"当时跑过什么"，不代表"现在还能再出一份"。
   加载后必须写明**配置已还原、需要重新运行**，绝不能让用户以为屏幕上看到的是新的那份。
2. **历史被淘汰要直说。** `backtest_history` 只留最近若干条。候选库的 `source_history_id`
   取不到（已经被淘汰）时，明确提示「来源研究的历史已不在本地，无法还原配置」，
   **绝不静默失败**——静默的后果是用户以为跳过去了、实际什么都没发生。
3. **漏字段是最容易犯的错，靠测试收口。** 每个页面补一条"还原完整性"用例：构造一份所有字段
   都**不是默认值**的 payload，加载后逐字段断言表单等于 payload。将来新加表单字段而忘记同步
   还原逻辑时，这条测试会红——这正是会静默出错的地方。
4. **自定义公式必须先解析再回填。** `parseCustomFormula` 会重置规则与排序值，顺序反了用户
   填的东西会被覆盖（踩过一次，组合回测页有注释）。这条规则同样适用于历史还原。

## 五、桥接方式

候选库 → 条件研究，走 sessionStorage（与已有的 `aquest.condition-research.apply`
同一套路），**不用 URL 参数**：request 是几百上千字节的 JSON，塞进 URL 既难看又有长度风险。

新的 key：`aquest.condition-research.restore`，条件研究页 `onMounted` 读到就走
`applyStoredRequest`，用完立即清除。
