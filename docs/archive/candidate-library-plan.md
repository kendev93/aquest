# 候选库 + 显式发布

backlog #4.3。改的是条件研究产出的**候选条件**的归宿：从「勾选 → 追加到规则 → 立刻重跑」的一次性动作，
变成一份持久的候选库，带采纳状态，**必须由人显式确认才发布，且发布后永不自动上线**。

## 一、为什么现在这个形态不够

调研确认的三件事，是这个功能的立项理由，不是背景描述：

1. **候选 id 只在一次报告里唯一**。`service.py::_mine_candidates` 生成的是 `buy-1` / `sell-3` 这种运行时
   序号，刷新页面就换了指向。没有任何东西能让你在下周指着「上次那个 lift 1.8 的条件」说话。
2. **证据跟着历史记录一起消失**。`BACKTEST_HISTORY_LIMIT = 20`，第 21 次研究跑完，最早那次的候选连同
   它的提升倍数、置换 p 值、留出期一起没了。
3. **「追加并重跑」不留下决定**。跑完就完了，没有「我当时认不认可这条」的记录，也没有「它后来变成
   策略了吗」的痕迹。

## 二、四条硬口径（改动前先读这段）

### 1. 永不自动上线

**发布 = 往策略库写一条 `tracking_status='off'` 的策略，仅此而已。** 发布路径里绝不调用
`StrategyTrackingService.launch`，也不设置任何定时上线。上线是策略追踪页的显式动作，因为上线日会冻结
研究段基线——这件事只能由人在想清楚的时候做。

发布响应里带 `online: false` 和一句说明，前端在结果区明写「未上线，要上线请到策略追踪页手动启动」。

### 2. 采纳与发布是两步

- `pending`（待定）→ `adopted`（已采纳）→ `published`（已发布）
- 不允许从 `pending` 直接发布（409，提示先采纳）。
- **绝不自动把「通过置换检验」的候选标成已采纳**：显著是统计结论，采纳是人的表态，两者不能互相冒充。
  唯一能把状态改成 `adopted` 的是用户点「采纳」。

### 3. 证据是快照，且必须标出处

入库时把当时的证据**整份复制**进库：提升倍数、置换 p 值、是否显著、支持样本数、覆盖标的数、
命中率与基线、留出期结果、滚动复验「N 窗中 M 窗优于基线」、参数敏感性保持率中位数、是否通过约束。
不回指历史记录——历史会被淘汰，候选不能跟着消失。

同时存 `source_history_id` 与研究区间，能溯源；列表上标注「入库时的快照」，避免被当成实时结论。

### 4. 发布不改证据、不给评价

发布只做一件事：把这条条件**按方向合并进来源研究那套配置**，生成一条组合回测策略。
不重算绩效、不打分、不在库里写「已验证有效」之类的结论。库里显示的永远是挖掘当时的数。

## 三、状态机

| 当前 | 可转到 | 条件 |
|---|---|---|
| `pending` | `adopted` / `rejected` | 人表态 |
| `adopted` | `published` / `rejected` / `pending` | 发布要二次确认；也可以反悔 |
| `rejected` | `pending` | 恢复成待定（否决不是删除） |
| `published` | `adopted` | **撤回**：删除由它生成的那条策略；若那条策略已上线则 409 拒绝，提示先去追踪页停止 |

`published` 不做「重新发布」：撤回后重新发布走同一条路径，不会产生第二条孤儿策略。

## 四、发布怎么拼出一套回测配置

来源研究的历史记录里存着完整的 `request_json`（日期在入库时已固化成绝对日期），所以发布不需要用户
从零填表：

1. 读 `source_history_id` 的 `request_json`；
2. 映射到组合回测请求（标的池、板块、公式、日期、手续费、滑点、成交方式、仓位模式、
   排序规则 + 槽位数）；
3. **按方向合并候选条件**（口径与前端「追加到规则」一致，后端是权威）：
   - 买入候选：追加进 `buy_rule.conditions`，`combine_mode` 保持来源研究的设置（收窄入场）；
     来源 `buy_rule` 为空（当初是持续满仓）时，用它替换成「只有这一条条件的买入规则」。
   - 卖出候选：追加进 `sell_rule.conditions` 且 `combine_mode='any'`（多一个离场触发）；
     来源 `sell_rule` 为空（当初是持有到期末）时同样替换。
   - 相同条件已存在则不重复添加，并在预览里说明。
4. 用 `PortfolioBacktestRequest` 校验——**猜不出来的一律报错让人补**，不悄悄填默认值蒙混。
   典型的就是排序规则：研究允许不带（`ranking_value=None`），组合回测必须有。这时预览返回 blocker，
   发布端点接受 `ranking_value` 覆盖。
5. `save_strategy` 落库，`tracking_status` 保持 `'off'`。

预览端点 `GET /{id}/publish-preview` 把第 2~4 步的结果（最终配置 + 警告 + 缺什么）先摊给用户看，
确认后才调发布。**「显式确认」不是弹个窗写「确定吗」，而是让人看见将要落库的是什么。**

## 五、不做的事

- **不给候选打分、不排名**。lift 高低是证据，不是评分；排序交给用户自己看。
- **不自动清理、不自动归档**。到期失效由人判断。
- **一次发布合并多条候选**。规则合并口径要能逐条核对，一次一条。
- **不接策略发现的候选**。`strategy_discovery` 的候选粒度是整套配置（带 `candidate_hash`），
  和单条条件差一个量级，混在一张表里两边都别扭。表留 `source` 字段，将来另开。
- **不做定时/自动上线**。见口径 1。

## 六、落地结构

后端 `aquest/candidate_library/`：`models.py`（常量与状态机）/ `evidence.py`（证据快照与溯源）
/ `publish.py`（配置拼装与条件合并）/ `service.py`（编排）。存储 `candidate_library` 表
（`SCHEMA_VERSION` 16 → 17，进 `ASSET_TABLES` 随资产备份导出），CRUD 照抄 `saved_strategies`。

前端新增 `/candidate-library` 页（列表 + 证据 + 状态操作 + 发布确认区），条件研究页候选操作区加
「加入候选库」（保留原有的「追加到规则并重跑」，它服务于另一件事：继续往下挖）。

## 七、测试要点

- 状态机每一条非法流转都拒绝（pending 直接发布、published 再发布、撤回已上线的策略）。
- 发布后 `tracking_status == 'off'`、没有 `launched_at`、没有追踪行——「永不自动上线」要能被断言。
- 入库是幂等的（同一研究的同一候选重复入库只跳过，不报错也不重复）。
- 来源历史记录已被淘汰时，入库返回 404 并说明原因，而不是静默失败。
- 条件合并：buy 保持 combine_mode、sell 转 any、空规则被替换、重复条件不重复添加。
- 迁移：v16 的真实 duckdb 文件打开后要有 `candidate_library` 表。
