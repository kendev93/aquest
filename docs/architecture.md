# 指标实验室架构

## 目标

应用是单机、单用户的本地行情分析工具。行情只保存在项目自己的 DuckDB（`market.duckdb`）里，由本项目内置的在线 provider 同步；项目既不读取也不写入任何外部行情软件的数据库，行情 schema 完全由本项目拥有。

```text
East Money 在线数据源 ──在线同步──► MarketDataSync + OnlineMarketSync
                                             │
                                             │ 有界 spawn 进程写分片
                                             ▼
                                  .sync-staging 分片 DuckDB
                                             │
                                             │ 主进程按标的事务合并
                                             ▼
                        本机 market.duckdb ──只读读取──► DuckDbMarketDataAdapter
              ┌──────────────────────────────┼──────────────────────────────┐
              ▼                              ▼                              ▼
       IndicatorCache                 行情页/指标                    回测与策略适配
       版本化派生指标                  DuckDb adapter                 自有交易核心
              │                              │                              │
              └─────────────── ScreenEngine / Backtest / Portfolio ─────────┘
```

## 分层规则

- `market_data/` 定义项目自己的行情模型、DuckDB 存储与仓库、行情适配器、在线同步的分片暂存与合并、自动同步调度、数据库维护和用户资产导入导出；它不写入任何外部数据库，也不存在跨进程同步锁。
- `indicators/` 保存可重建的版本化指标缓存；缓存不是行情事实源。
- `adapters/` 通过 provider 路由接入项目自有在线客户端；East Money 是唯一在线 provider（HTTP 接口，免费且不需要 key），覆盖 A 股主板/科创板/创业板股票。系统只研究 A 股：基金（含 ETF）、指数、债券和 B 股既不在线同步也不本地导入（B 股流动性枯竭，回测的成交假设在它身上不成立）。
- `formulas/` 是无副作用的数组计算层。公式函数由 `formulas/tdx_math.py` 自己实现，输入输出均为项目内部的 NumPy/Pandas 数据。
- `screening/` 负责条件合并、批量读取、单标的容错、进度和导出，不处理网络或文件格式。
- `backtest/` 负责单标的交易模拟和绩效计算；`portfolio_backtest/` 负责动态候选、固定槽位和补位；`strategy_fitness/` 复用这些交易语义完成时间切分评估。
- `web/` 负责 Pydantic 校验、任务提交/轮询、任务互斥分组和安全错误响应。正式 Docker 运行时，策略发现、二次优化和榜单复核由独立 `strategy-worker` 执行；worker 使用容器内认证 API 上报领取、进度、取消和结果，backend 是 DuckDB 的唯一写入者。worker 对 Indicator Lab 数据库只读，计算期指标缓存留在内存，普通任务继续使用进程内 runner。
- `web-ui/` 负责行情状态展示、同步范围表单、进度和图表；同步入口是一键在线同步和 East Money 全量补齐，应用不提供本地行情文件导入。

在线行情客户端是项目内置实现，不引入财经数据客户端依赖；业务层只依赖项目自己的 provider 接口和规范化 DataFrame。East Money 是唯一在线 provider。项目保留自己的 `.day` 读取器和兼容适配模块（本地文件导入用），但默认装配不使用它们，应用启动时也不会扫描或导入本地通达信文件。

## DuckDB 数据层

默认数据库路径为 `${SELECTOR_DATA_DIR}/market.duckdb`；未设置环境变量时使用用户数据目录 `~/.indicator-lab`。Docker 将 `SELECTOR_DATA_DIR` 设置为 `/data/market`，并用命名卷 `indicator-lab-data` 持久化；叠加 `docker-compose.bind.yml` 时改为 `${DATA_DIR}` 的宿主目录绑定挂载，此时宿主目录必须允许容器内 `appuser`（uid 10001）写入。这个库是行情的唯一事实源，也只由本项目写入。

核心表：

- `instruments`：市场、代码、中文名、品种类型、板块、首末日期、K 线数量、源状态和最近一次 provider；`source_path` 是兼容列，在线同步写入 NULL；
- `daily_bars`：原始价格口径的 OHLCV、成交额、来源、具体 provider、K 线状态和导入时间，`(market, code, trade_date, price_basis)` 唯一；
- `data_meta`：schema 版本、最近一次在线同步时间、provider 版本及证券列表指纹。
- `indicator_cache`：按标的、周期、价格口径、内置公式版本和行情指纹保存完整指标数组与信号数组；缓存失效后可从 `daily_bars` 重建。
- `custom_indicator_cache`：按标的、周期、价格口径、自定义公式哈希、参数哈希、公式引擎版本和行情指纹保存自定义输出。
- `strategy_discovery_history`：策略实验请求、候选榜单、算法元数据、开始/结束时间和耗时；默认保留最近 20 次实验。
- `strategy_discovery_replay_history`：当前夏普榜或收益榜前十的全行情复核结果、连续资金曲线、成交记录、分段绩效、数据指纹和复核耗时；同一实验和榜单只保留最近一次，删除实验时级联删除。
- `strategy_jobs`：策略实验、二次优化和全量复核的请求、状态、进度、结果、取消标记、worker 租约及时间戳；只由 backend 写入，旧版 `.strategy-jobs` JSON 在首次启动时幂等导入。
- `screen_history`：公式筛选的请求元数据、计数摘要和完整结果 JSON，默认保留最近 10 次。
- `backtest_history`：组合和策略适配性回测的请求快照、完整结果、摘要、开始/结束时间和耗时；按回测类型分别保留最近 20 次，买卖条件研究与波段研究也写入该表（波段研究存的是第二步的完整参数，外加第一步表单与结果的存档快照）。历史遗留的 `single_stock` 记录仍保留在库中，但单股回测页面与 `/api/v1/backtests` 路由已移除，其单票能力并入组合回测的「指定标的」。

行情事实写入只由本项目的主进程执行：在线同步的 provider worker 先把规范化结果写进各自的分片数据库，再由主进程按标的事务合并；派生指标缓存可由预热任务或业务请求按需填充。库内并发写由进程内写锁和 DuckDB 连接串行化，跨进程不再有 lease 锁或锁文件，策略 worker 始终以只读方式打开同一数据库。读操作每次建立独立只读 DuckDB 连接。全市场筛选、组合回测和策略适配通过一次批量查询得到各标的分组，不逐标的往返查询。

## 策略实验资源与任务队列

策略实验默认使用本地最新已完成日线往前 5 个日历年；用户可以选择全历史或显式开始/结束日期。系统先统计目标日期窗口内的行情行数并估算快照和 worker 工作集。`SELECTOR_DISCOVERY_WORKERS=auto` 会先按容器可见 CPU 形成最大并发，再按 `SELECTOR_DISCOVERY_MEMORY_BUDGET_MB=auto`（容器/主机可见内存的 80%）选择实际 worker 数；也可以设置整数作为并发上限或固定内存预算。即使一个 worker 也超预算时，在创建任务前返回结构化错误，不静默截断用户选定的日期范围。

快照构建按标的批次执行：完整行情指纹单独流式计算，指标计算只读取 warm-up 加实验窗口，数值数组写入只读 memmap。worker 的标的上下文和日期索引均有界，日期查找使用排序数组而不是每个进程重复建立完整 Python 字典。

正式 Docker Compose 包含独立 `strategy-worker` 服务。backend 与 worker 共用数据目录里的同一个 token 文件（首次启动由 backend 自动生成），worker 只读取它作为 bearer secret；worker 仅通过未公开到 OpenAPI 的容器内接口领取任务、上报进度/心跳/取消和完成/失败结果。所有任务状态及最终历史均由 backend 写入同一 DuckDB；过期 worker 租约会由 backend 标记为失败。容器重建不会影响数据卷中的策略任务或历史。

在线同步完成后会分批预热内置公式；已有数据库或预热未完成时，筛选和回测会按需填充缓存。缓存基于完整、有序行情的 SHA-256 指纹，公式版本变化、行情更新或价格口径变化都会自动跳过旧缓存。自定义公式按公式内容、参数和引擎版本独立缓存，不同参数不会互相复用。

schema 版本变化或维护备份时，初始化逻辑会先生成带时间戳的 `.bak-*.duckdb` 副本，并在复制成功后只保留最近一份；该备份超过 `SELECTOR_DB_BACKUP_RETENTION_DAYS` 天后自动清理，再执行升级（默认 3 天；独立分发编排默认设为 0，表示压缩期间临时保留一份用于回滚、成功后立即删除）。更高版本数据库会拒绝打开，避免静默破坏数据。数据库文件和备份均不提交 Git。应用空闲时会检查数据库物理文件是否比上次成功整理后的大小增长至少 50%；达到阈值后通过同目录临时库和 `COPY FROM DATABASE` 重写，校验表行数及 schema 后才原子替换，并把上一份库以硬链接保留为备份而不是整库拷贝，因此压缩峰值是两份库大小而不是三份；整理状态写入 `data_meta`。旧版 `market.maintenance.json` 会在首次维护时导入该元数据表。

## 行情来源与写入边界

本机 `market.duckdb` 是行情的唯一事实源：只由本项目写入，也不与任何外部软件共享。应用不扫描、不解析、不导入本地通达信 `.day` 文件；项目自有的 `.day` 读取器和兼容适配模块仅为兼容保留，默认装配不启用它们。

在线同步的网络 worker 只把规范化结果写进数据目录下的 `.sync-staging/<run_id>/` 分片数据库，主进程在 worker 全部结束后按标的事务合并进主库，合并按 `(market, code, trade_date, price_basis)` 幂等去重。同一时刻只允许一个行情同步任务在跑，由任务执行器的互斥分组保证，不再需要跨进程锁文件。

## 用户资产备份与恢复

`market_data/transfer.py` 导出用户无法重建的记录：`backtest_history`（含单股、组合、策略适配、买卖条件研究和波段研究）、`screen_history`、`strategy_discovery_history` 和 `strategy_discovery_replay_history` 四张表，打包成一个 zip。行情和指标缓存刻意不导出，它们总能重新同步或重算；一份完整安装里资产约 13 MB，而数据库本身在 GB 量级。

归档内容是每张表一个 JSONL 条目，外加 `manifest.json`（格式标识、格式版本、schema 版本、逐表行数与列名、导出时的行情规模）。导入是幂等合并：主键已存在的记录记为 skipped，不覆盖也不删除；备份里出现当前 schema 不认识的列、或备份来自更高的 schema 版本时，在写入前直接拒绝。上传上限为 1 GiB。

接口为 `GET /api/v1/data-transfer/manifest`、`GET /api/v1/data-transfer/export` 和 `POST /api/v1/data-transfer/import`；命令行入口为 `python -m selector_app export [-o 目标]`、`python -m selector_app import <zip>` 和 `python -m selector_app manifest <zip>`。

## 在线同步

在线同步 provider 是 East Money：它用内置 HTTP 客户端拉取证券列表和日线，免费且不需要密钥，覆盖 A 股主板/科创板/创业板股票，单只股票的日线请求失败时切换腾讯日线接口。范围校验不通过时在发起请求前直接报错，而不是静默跳过。同步前先查询本机库的已有覆盖，完整区间跳过，中间缺口只覆盖所选区间，首尾缺失只请求缺失范围。

证券列表在服务端按板块收窄（`fs=m:0 t:6,m:0 t:80,m:1 t:2,m:1 t:23`），避免拉取全市场再丢弃大半；East Money 会把每页硬截成 100 条，所以翻页以响应里的 `total` 为准，不能把"返回行数少于请求页大小"当作最后一页。接口限流时会返回 HTTP 200 + `rc != 0`（或直接断开连接），这两种情况都会被转成 `OnlineProviderError` 并按目录专用退避重试，不会伪装成"证券列表为空"的成功同步。

在线同步不写回 `.day`，也不修改任何外部文件。provider 使用有界的 `spawn` 进程池，每个 worker 把结果写进自己独立的分片 DuckDB（`market_data/staging.py`，最多 8 个 worker，分片位于数据目录的 `.sync-staging/`），全部结束后由单一主库写者按标的事务合并；活动任务可通过 `/jobs/active` 查询并通过 `/jobs/{job_id}/cancel` 协作取消。`/api/v1/market-data/capabilities` 会报告当前执行模式、worker 数和分片目录。

在线证券列表的 `name` 字段会写入 `instruments`，并在扫描结果 JSON/CSV 和页面中透传。名称刷新失败不会影响已有行情扫描，结果显示 `—` 作为占位。内置公式的扫描结果只透传注册表中的用户可选输出，公式内部中间数组仍保留在指标缓存中；自定义公式透传其命名输出。

在线同步在请求日线前应用同一套市场、证券类型和板块范围，因此未选中的品种不会产生行情请求。一键同步只拉取在线证券列表并补充在线日线，也不会被本地行情子集限制。筛选、组合回测和策略适配复用该范围模型；没有设置类型或板块过滤时使用在线证券列表中的全部可识别品种，不设置项目级默认偏好。仅供内部快速更新既有标的的 `prefer_store_targets` 模式仍保留，但不用于普通 API 或自动同步。

## 公式和回测一致性

项目自有 `REF`、`SMA`、`EMA`、`MA`、`STD`、`AVEDEV`、`SQRT`、`LLV`、`HHV`、`SUM`、`COUNT`、`BARSLAST`、`CROSS` 等函数，保留现有 NaN、预热和 `SMA(..., 3.2, 1)` 语义。公式一的负分母、公式二显式 `REF(A,20)` 间隔和自定义公式的因果边界均有回归测试。

指标缓存始终基于完整历史计算，再由筛选或回测截取日期窗口；不会只对可见窗口计算，从而保留均线、`REF`、`EMA` 和穿越信号的预热语义。缓存异常只影响性能，不会替代原始行情或阻断直接计算回退。策略实验的行情快照同样遵循这条约定：窗口前额外读取的预热根数取各公式 `recommended_bars` 的最大值（当前 268，由需要 250 根标准化窗口的 `rsrs_zscore` 决定），而不是 `minimum_bars`。只有后者时窗口内绝大多数日期的长窗口输出仍是 NaN，挖掘排名会与走全历史的组合复核系统性不一致。

单股交易核心使用下一根开盘/收盘成交、100 股整数、佣金最低收费、印花税、滑点和资金不足时的 reduce 规则。只研究股票，因此交易参数只有一档：佣金 `0.0001`、最低 `0.1` 元、印花税 `0.001`。所有调用点共用同一个解析函数，避免同一只标的在研究和组合回测里算出不同成本。

### 基准对照（组合回测）

组合回测报告带一条**标的池等权买入持有**基准（实现：`portfolio_backtest/benchmark.py`）。口径是我们自己定的，不抄外部指数：

- 标的池 = 本次回测真正参与模拟的那批标的；**不是**沪深300 之类的外部指数。库里没有指数数据（只研究股票），而且"跑赢一个自己挑的指数"容易变成幸存者偏差式的自我安慰——真正要回答的是「这套选股规则，是不是比把这批股票各买一点然后不动更强」。
- 回测窗口首日按收盘价等权买入全池，持有到最后一天；**不计佣金/印花税/滑点、不考虑整手与现金拖累**，因为它是拿来比的尺子，不是真去执行的策略。给基准加摩擦只会让两边口径不一致。
- 首日没有价格的标的（新股、长期停牌）**直接排除**，不用后面的价格回填——回填等于默认"上市前就买得到"，会把幸存者偏差塞进基准。之后的缺失交易日沿用前收盘价（停牌期间价格不变，不是收益为零）。
- 与策略同一笔本金、同一段区间、同一批交易日，因此总收益/年化/夏普/最大回撤可以直接相减。前端展示"超额年化"（策略年化 − 基准年化）并把基准虚线叠在同一张资金曲线上，纵轴范围同时装下两条线。
- 基准绩效只保留与策略可比的那几项（总收益、年化、回撤、回撤持续、夏普、索提诺、卡玛、波动、期初/期末）。成交笔数、胜率这类对"买入不动"没有意义，留在基准里只会误导。
- 窗口不足两个交易日、池内没有可用标的、本金不为正时算不出基准：报告其余部分照常，`benchmark` 为 `None`。

### 策略库（保存 / 载入 / 删除）

`saved_strategies` 表 + `/api/v1/strategies`，入口是组合回测页内嵌的「策略库」面板。它和 `backtest_history` 是两回事：历史记录的是"跑过什么"（每类默认保留最近 20 条，满了自动淘汰），策略记录的是"还想再跑一遍"（只有用户显式删除才消失，不设上限）。

- 一条策略 = 一份可重放的组合回测配置 + 保存时的绩效快照。**保存时用 `PortfolioBacktestRequest` 全量校验**，跑不起来的配置（不存在的指标、缺卖出规则、非法区间）在保存时就被拒，不会等到追踪重算那天才炸。
- **相对日期区间在保存时固化成绝对日期**：`近五年` 这类模式存下来会让三个月后的重算滑到另一段样本，等于没复现。固化后 `date_mode` 一律写成 `custom`，载入时日期选择器回到具体区间。
- 只存绩效快照（`_strategy_summary` 白名单 + 基准绩效），`equity_curve` / `trades` / `states` 不进策略表——它们动辄上万行，复制进每条策略会让库膨胀、列表每次读都要反序列化几 MB。
- 名称唯一（表级 `UNIQUE` + 保存/改名前的显式查重），最长 60 字符，备注 500 字符。改名只动名称与备注，**配置保持不变**；想换配置就重新保存一条。
- 删除是二次确认（列表里第一下只把按钮换成"确认删除"），避免误删研究成果。
- 表写在 `ASSET_TABLES` 里，随用户资产备份导出/导入——策略是用户研究成果，丢了无法重建。

策略实验室复用组合回测的数据适配器、指标缓存和交易模拟器。它固定用户给出的 `max_positions`，只搜索排序指标/方向、刷新频率、买卖规则及风险参数；排名变化只用于补空槽。搜索候选使用 Optuna TPE，LightGBM 只作为候选提议 surrogate。真实组合回测在每次实验开始时生成一次只读内存映射行情/指标快照，自动 worker 只映射并复用这份快照，实际并发由 CPU 上限和数据/内存预检共同决定；候选阶段只重算规则掩码和组合模拟，并以摘要模式跳过持仓状态和排名事件构建；主进程在批次完成后统一更新搜索状态，surrogate 只在新增样本达到重训间隔时更新，大预算搜索在长期无改善时保守提前收敛。最终评价始终由真实组合回测完成。Docker 正式运行时两项依赖由 `requirements.lock` 安装并强制要求；确定性随机搜索仅在显式 `INDICATOR_LAB_DISCOVERY_ALLOW_FALLBACK=1` 的本地诊断模式开放。

策略实验按寻优/验证/最终留出三段运行，验证阶段分别保留 Sharpe 与年化收益目标的候选池，候选哈希去重后共同完成验证。验证结果逐个进入两个独立的前十保持器：同一交易行为在夏普榜内保留夏普更高的代表，在收益榜内保留年化收益更高的代表，两个榜单互不共享去重状态；最终留出不参与排序。用户必选买入/卖出条件会在候选生成阶段固定加入，并在快照阶段预计算条件掩码；候选只搜索剩余条件名额。完整请求、候选配置、三段指标、数据指纹、算法版本和随机种子写入 `strategy_discovery_history`，并记录自动搜索开始/结束时间和耗时，默认按最近 20 次保留。单股、组合和策略适配性任务成功后写入 `backtest_history`；列表接口只读摘要，详情接口才读取完整结果。

排行榜页面可以对当前夏普榜或收益榜前十发起独立异步全量复核。复核使用实验原始开始日期和任务启动时本地最新已完成行情日，自动共享只读行情/指标快照，并按 CPU 和资源预检选择实际并发；每个候选只模拟一次，整体、今年以来、滚动一年/两年和自然年度指标均从同一条连续资金曲线派生。复核结果不参与排行榜排序，行情指纹变化仅标记为“行情已更新”；页面可展开完整配置、资金曲线和成交原因，并把完整区间配置应用回普通组合回测。

## 买卖条件研究

买卖条件研究是独立于策略实验室的单股规则挖掘流程。用户给定的基础买入和卖出规则固定保留；买入候选作为额外 AND 过滤条件，卖出候选作为额外 OR 退出触发。基础买入与卖出规则都可以留空：卖出留空表示“持有到期末”，买入后不主动卖出，由回测在最后一根 K 线按收盘价平仓（市值那部分权益曲线已经计过，因此只把手续费从最后一天的总权益中扣除，净值口径才会与成交记录一致）；买入留空表示“持续满仓”，每根 K 线都是候选买点，实际表现为每次离场后下一个交易日立即再买入。两侧恰好是各自合并运算的单位元——买入候选是 AND 上去的，空基础取“恒真”；卖出候选是 OR 上去的，空基础取“恒假”——所以基础为空时挖出的候选就是那一侧的完整规则，而不只是基础规则之上的微调。留空也是唯一能构造出样本的办法：没有买入就不会有成交、没有持仓就谈不上提前离场。两侧不能同时留空，至少要保留一侧作为研究基准。所有股票分别使用同一单股交易模拟器、费用和成交语义回测，不共享资金，也不限制跨股票的持仓数。挖掘特征只取指标目录中可跨股票比较的输出：以货币计价的均线、MACD 和原始价格被排除（否则跨股票阈值退化成“按股价排序”），趋势偏离、波动率和量能改由 `乖离率20`、`ATR%`、`量比5日` 等无量纲输出承担。候选池只含股票：ETF 大量跟踪同一指数，指标排序下会选出高度雷同的标的，指数又不可交易，把它们混进池子会让切分点被样本量大的一类拉走。

研究还会给每个买入候选附一份「前 N 名」只读诊断：把同一信号日命中该条件的股票按排序规则排一次，只保留前 N 名再重算胜率。它回答的是组合回测里真正会发生的事——买入条件决定谁有资格进候选池，排序决定谁抢到有限的槽位，而研究本身不设槽位上限，两者口径天然不同。诊断不参与挖掘排序，只在候选表格里与全池胜率并列展示；命中数没超过槽位数的交易日不计入，所以 `top_n_filtered_days` 为 0 时这一列等价于全池，界面会明确提示排序没起作用。卖出候选不做这个诊断，因为槽位竞争只发生在入场。排序值取用户指定的，没指定则用推荐值——推荐只依赖信号样本、不依赖挖掘结果，因此可以先算出来再喂给挖掘阶段。

研究任务分寻优、验证和最终留出三段。寻优段先从已完成交易抽取入场特征和持仓期退出决策样本，以净盈利交易或“提前退出优于基础退出”的样本作为目标，使用分位阈值和跨指标比较生成可读规则；卖出挖掘每笔交易最多采样 8 个均匀分布的持仓决策点，候选规则仍在完整日线上重放。候选按支持样本、覆盖股票数和相对基准胜率 lift 筛选。每只股票在每一阶段只准备一次行情和指标数据，随后在内存中复用已计算指标重跑候选规则。每只股票的行情指纹在各阶段保持一致；任务期间数据变化时终止研究，避免不同阶段混用行情。候选回测使用 summary-only 模式，只生成绩效所需的日净值和成交统计，不保存每个候选的逐日持仓明细；最终结果仍包含逐股票绩效摘要。

同一个发现会有多种写法——同一指标只差一个分位阈值，或者两个同向的指标——照单全列会让人误以为挖到了好几条条件。筛选之后挖掘还会按命中向量的 φ 系数合并同义条件：相关性达到门槛（默认 0.6）时只保留排序最好的那条，其余挂在它的 `duplicates` 里一起展示，**不静默丢弃**。φ 只在两条条件都可评估的样本交集上算（各指标有自己的缺口，不在交集上算等于白送命中）；取 ρ ≥ 门槛而不是 |ρ| ≥ 门槛，因为 ρ ≈ −1 是互补条件（一条的反面），不是同一个发现。默认 0.6 下同一指标的相邻分位阈值（ρ ≈ 0.61~0.67）合并，相隔一个分位的（ρ ≈ 0.41）保留为独立候选——后者是不同的激进度，不是重复。合并空出的名额由排序更靠后的不同义条件顶上，所以合并不会减少候选条数。细节见 `docs/duplicate-merging-plan.md`。

每个候选还带一条**阈值邻域曲线**：把切点往松、往紧各挪两档（分位 ±5% / ±10%）重新计分，给出每档的保持率 `(lift−1)/(基点 lift−1)`，用来分辨「切点站在台地上」还是「只有一个数好用的悬崖」。扰动走分位而非阈值百分比（量纲无关，且「A > B」这类条件没有常数可挪），度量沿用挖掘口径，基点用原始阈值直接算所以与候选表同一个数；命中样本不足或退化到恒真的档位不计入统计，也不给稳健度评分。**邻域是在挖掘样本（寻优期）上算的，只说明这个切点是不是噪声尖峰，不代表样本外表现。** 细节见 `docs/sensitivity-plan.md`。

验证段按跨股票合并成交胜率提升、盈亏比、平均单笔净收益、成交数和覆盖股票数筛选候选；默认每侧最多挖掘 5 条规则，每侧取 1 条进入最终留出。最终留出结果不参与搜索和排名。跨股票总胜率和盈亏比按独立股票的平仓成交汇总；收益率、最大回撤和 Sharpe 只按个股计算并展示分布，不生成或暗含组合净值。

### 排序规则推荐与组合回测桥接

研究逐只独立回测，天然回答不了「同一天几只都符合条件时该买谁」——而组合回测恰恰是「买入条件决定谁有资格进候选池，排序决定谁抢到那 N 个槽位」的模型。为此研究在结果里附带两块只读结论，都不改变研究自身的评估口径：

**日均命中股票数。** 用挖掘样本自带的信号日期按日去重统计：买入样本数 ÷ 有命中的交易日数。拿它跟槽位数比大小就能判断条件是否还有话语权——命中 3 只时条件说了算，命中 300 只而只有 5 个槽位时真正决定买谁的是排序。

**排序指标推荐。** 挖掘阶段本来就为每只股票算过全部可排序指标，所以推荐不需要重算指标，只把买入样本按信号日拼成横截面面板即可。`condition_research/ranking.py` 对每个候选排序值算三条互相独立的证据：

| 证据 | 算法 | 回答什么 |
|---|---|---|
| 平均信息系数 | 每个信号日上排序值与收益的斯皮尔曼秩相关，取均值 | 这个指标本身有没有预测力 |
| 信息系数信息比率 | 信息系数均值 ÷ 标准差 | 这个准头稳不稳 |
| 分段同号 | 按时间等分 6 段，看几段的方向与总体一致 | 是贯穿始终还是某段行情的运气 |

另附两项辅助判据：分层收益（每个信号日按指标值五等分，看各档平均收益是否单调）用于识别「收益只集中在极端尾部」，前 N 名提升（只买当日排名前 N 的股票相对全部命中信号的收益差）用于量化效果。信息系数为负不丢弃，而是把推荐方向翻成升序——反着用也是一种用法。

**推荐按稳定性排序，不按提升幅度排序**：31 个指标 × 2 个方向共 62 次试验，挑提升最大的那个必然挑到噪声。置信度分证据充分 / 可用 / 证据不足三档，样本不足 20 个信号日、绝对信息系数低于 0.02、或过半时间段反向时一律降级并说明原因，绝不照推。

研究页可以指定排序指标、方向和槽位数（下拉只列 `rankable` 输出），它们随请求一起存入历史记录；「用这套规则去跑组合回测」把买卖规则、排序规则（未指定时用推荐值）和槽位数写入 sessionStorage 后跳转，组合回测页在挂载时读取回填。

任务运行在通用后台任务执行器中，支持进度、取消和错误摘要；成功结果写入 backtest_history 的 condition_research 类型，并可从历史接口加载。逐股票的训练、验证和留出复验按股票拆分为独立任务，通过 spawn 进程池并行执行：每个 worker 自行以只读方式打开行情库、一次只处理一只股票，只回传精简报告和挖掘样本，行情聚合、条件挖掘、约束过滤和排序仍由主进程完成。worker 数由 `SELECTOR_CONDITION_RESEARCH_WORKERS`（默认 `auto`，取可见 CPU 的一半，上限 8）或显式整数决定，并按数据量做内存预算：worker 侧约 `224 MB + 2 KB × 每标的 K 线数`（实测与规模弱相关），主进程侧随股票数和候选数线性增长（实测每股票约 384 KB、每个股票候选组合约 8 KB），两者之和必须落在 `SELECTOR_CONDITION_RESEARCH_MEMORY_BUDGET_MB`（默认取容器/宿主内存的 80%）内。预算只够部分 worker 时按实际值降级；连单进程都放不下时在创建任务前返回 422 并给出估算明细，不会启动必然 OOM 的任务。无法重建的注入了自定义适配器的场景自动退回进程内执行。

## 单指标 / 因子检验

`selector_app/factor_test/` 回答的是一个更前面的问题：**某个指标本身能不能给股票排序**。它不依赖任何规则、信号或回测，标签就是「从当日收盘到 N 个交易日后的收盘」的前瞻收益（`horizon`，默认 5 个交易日）。

面板形状是「指标 × 股票 × 交易日」，两遍读行情建出来（第一遍只建日期轴），走与波段研究相同的**预算三道墙**（自身上限 → 可用内存的一半 → 临时目录余量），超了在跑之前拒绝并说清撞在哪道墙。

**独立单位是交易日，不是单元格。** 5000 只 × 1000 天看着是 500 万个观测，但股票共用同一个市场时钟——周二集体反弹时周三的标签基本是同一个故事。所以秩相关在每日横截面内做，置换检验按**连续日期块**整块搬动（逐日打乱会低估噪声）。置换走 **Gram 矩阵**：一次算出所有「第 t 天的值 vs 第 u 天的收益」的相关，实测 IC 在它的对角线上，一次日历置换只是换一批格子，200 次置换不必重算 20 万次相关。

**证据一律是差值，不是比值。** 波段研究的标签是事件，用命中率之比很自然；这里的标签是能取负的收益，两个负数相除会读成「差三倍」而实则是「亏得少」。所以证据是分层收益（每日按指标值分档，看各档平均收益是否单调）+ 多空价差（首档减末档）。多空曲线**累加不复利**（持仓期重叠，复合出净值会凭空放大），t 值按 `N/h` 折算独立样本。

三条护栏是真机跑通之后补的：**p 值过了但 IC 只有噪声门槛的 1.0 倍不许说「强度可观」**（`CLEAR_IC_RATIO = 2.0`）；**分层倒挂容差取整条阶梯跨度的 5%**（否则前三档只差万分之一也会被报「3 处倒挂」——在噪声上响的警告比没有警告更糟）；**多空胜率 < 55% 要直说「接近抛硬币，扣掉成本未必可执行」**（排名是真的不等于可执行）。前后半段的符号必须内部留着：对外存绝对值（符号已用在「买高还是买低」上），但「方向相反」是符号的命题，从绝对值上读永远触发不了。

**不做样本外切分**：方向是看全样本的符号定的，前后半段一致只说明「不是某一段独撑」，页面上照此写出来。31 个指标 × 多个前瞻天数的多重性由 BH-FDR 统一校正。细节见 `docs/factor-test-plan.md`。

## 回测历史对比

`selector_app/history_compare/` 把散在各处的 `backtest_history` 记录拉到同一张表里：**只读历史，不重跑任何回测**。取数在 `extract.py`（按类型抽曲线与指标），编排与可比性判断在 `service.py`。

**曲线口径只有三种，不同口径绝不叠绘**：资金曲线（`portfolio` / `single_stock` 的 `equity_curve[].total`）、多空累计价差、累计 IC（后两者只来自 `factor_test`）。条件研究、波段研究、策略适配性**都不产生曲线**——它们只能比样本规模、显著性与各自的专属指标。因子类曲线**不做归一化**（没有本金概念），画进净值图里会被当成收益曲线。

**净值归一化只除以本金**（`performance.start_cash`），取不到才退回除以首值，并在结果里写明用了哪一种。曲线点数上限 1200，超出等距抽样但首尾必留。

**跨类型只比规模与显著性**：统一指标表的每一格都带 `source`（如「组合资金曲线」「逐标的 test 段中位数」「最强候选 · 留出期合并交易」），拿不出来的格子显示「—」+ 原因，绝不用 0 填。可比性警告（曲线口径混杂、区间不重叠、类型混合、样本长度差 ≥3 倍）由服务端生成，前端只负责展示。细节见 `docs/history-compare-plan.md`。

## 标的检验台

`selector_app/instrument_lab/` 回答一只票的三个问题：它在已有指标上取过什么值（`values.py`，
复用 `BacktestService.prepare_for_ref` 的 `feature_values`，走指标缓存）、一组规则放到它身上跑成
什么样（直接调既有的 `BacktestService.run`）、**在全市场通过置换检验的条件放到它身上还成立吗**
（`conditions.py`）。条件库从 `condition_research` 的历史里只取 `significant=True` 的候选。

**不打分。** 没有权重就没有可证伪的依据，所以只给读数。证据一律是**差值**（命中组前瞻收益
均值 − 全样本均值，百分点），显著性走连续日期块置换（复用 `swing_research.scoring` 的
`block_permutations` 与 `benjamini_hochberg`，与因子检验同一口径）。命中 < 20 标「样本不足」
且**不判显著**；可用交易日 < 60 不做置换；分位是**自身历史分位**，不是全市场排名。细节见
`docs/instrument-lab-plan.md`。

## 筛选方案

`selector_app/screen_presets/` 把公式选股页整套可复现的输入存成命名方案，落在
`screen_presets` 表（在 `ASSET_TABLES` 里，随用户资产备份导出）。`payload.py` 只做一件事
——**白名单裁剪**：不认识的字段丢弃、越界值钳回合法区间，改了什么写进 `notes` 一并返回。
`service.py` 收口名字唯一性与条数上限（200）。

存的内容只有输入：信号 / 条件 / 市场范围 / 板块 / 并发 / 周期 / 自定义公式。**结果、任务
状态、页码都不存**——结果依赖当时行情，存下来下次加载的人会以为它还成立。

行情查询接口不需要 `vipdoc_path`；请求体里仍保留该字段只为兼容旧客户端，行情统一来自本机 `market.duckdb`。自定义 universe 文件仍可由筛选/回测请求指定，但其中的行情数据来自数据库。

本机版没有任何鉴权：`GET /api/v1/authorization/status` 恒定返回 `required=false`、`available=true`、`can_access_core=true`、`access_state=unrestricted`（`本机版不校验会员`）。此前跟随共享行情架构存在的机器绑定会员校验已完全移除，接口形状暂时保留，供将来接入微信小程序账号登录使用。
